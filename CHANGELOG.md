# Changelog

All notable changes to OrionBelt Semantic Layer are documented here. Releases before 3.0 are in [CHANGELOG-archive.md](CHANGELOG-archive.md).

## [Unreleased]

### Added

- **Swagger UI's Authorize button takes the credentials the API accepts.** With authentication on, the OpenAPI document declares them on every `/v1` operation, so `/docs` shows **Authorize** and sends what is pasted there: an API key in `api_key` mode; under `oidc` an access token, or an API key when `API_KEYS` is set. `AUTH_MODE=none` changes nothing. See [Swagger UI](docs/guide/authentication.md#swagger-ui-docs).
- **Arrow Flight SQL and the Postgres wire protocol accept the OpenID Connect provider's access tokens under `AUTH_MODE=oidc`, and run as the token's user.** Flight takes the token as the password of a Basic credential or as `Authorization: Bearer`, and checks it on every call. pgwire takes it as the password over TLS only (`sslmode=require`): on a TLS connection it asks for a cleartext password, which TLS protects, since SCRAM cannot check a token; a connection stays open after its token expires, as a Postgres connection does. Both need `obsl:read`, and both refuse a bad token with its reason (`Token has expired`). Each call (Flight) or connection (pgwire) runs as its caller, so one user's session is not reachable by another over these surfaces either, as on REST; a Flight ticket or prepared statement can be redeemed, bound, run or closed only by the caller that received it. API keys keep working on both, with or without TLS. pgwire under `oidc` refuses to start with neither `API_KEYS` nor `PGWIRE_TLS_CERT`. See [the other surfaces under `oidc`](docs/guide/authentication.md#the-other-surfaces-under-oidc).
- **`AUTH_MODE=oidc`: the REST API accepts the access tokens of your OpenID Connect provider.** Set `OIDC_ISSUER` and `OIDC_AUDIENCE`; OrionBelt reads the provider's signing keys from its discovery document (or `OIDC_JWKS_URI`, or `OIDC_JWKS_FILE` for air-gapped installs) at startup, refuses to start when it cannot, and fetches them again when the provider rotates them. A token must be signed with RS256, PS256, ES256 or EdDSA, come from the issuer, name the audience, not be expired and have a `sub`. Its scopes come from the `scope`, `scp` and `roles` claims (`OIDC_SCOPE_CLAIMS`, dot paths such as Keycloak's `realm_access.roles` included), and `OIDC_SCOPE_MAP` maps IdP role names to `obsl:read`, `obsl:write` and `obsl:admin`. Each user sees only their own sessions. A bad token answers 401 with `WWW-Authenticate: Bearer error="invalid_token"` and the reason, a missing scope 403 with `error="insufficient_scope"`. Keys in `API_KEYS` stay valid next to the tokens, as service keys: Arrow Flight SQL, the Postgres wire protocol, the UI and MCP use one, since they do not take the provider's tokens yet. See [OpenID Connect](docs/guide/authentication.md#openid-connect), with notes for Keycloak, Microsoft Entra ID and Auth0.

- **OBSL names itself to the databases it reads, as `orionbelt-semantic-layer/<version>`.** The name shows next to OBSL's queries in each database's own history: as the User-Agent on BigQuery, ClickHouse, Databricks and DuckDB (MotherDuck, and DuckDB's HTTP reads), as `application_name` on Postgres, and as the `program_name` connection attribute on MySQL. Snowflake and Dremio get none: Snowflake's `application` is for its registered partners. The six drivers take a new `client_name` argument for this; unset, a driver sends its vendor library's default, as before. The Data Sources guide lists where each database shows it. On MySQL a `client_name` with a comma goes through PyMySQL, since the ADBC driver would split it into two attributes; `backend="adbc"` refuses it.

### Changed

- **One sort icon per result column, which cycles through unsorted, ascending and descending.** Query Results headers showed `▲ ▼ ✕` on every column, and the always-visible `✕` (stop sorting by this column) read as "remove the column". Each header now has one icon of two stacked triangles: both dim while the column is not sorted, the active one orange; a click moves to the next state, and its tooltip says what the click will do.
- **A filtered result column shows a filter icon in its header, with a `✕` that removes just that filter.** A click on a cell adds an `equals` filter (or `IS NULL`) for that column; until now the only ways out were clicking the value again or "Clear filters", which drops all of them. The icon's tooltip shows the filter (`Client Name = Kai Garcia`). The "Clear filters" chip stays, and now leads with the same filter icon. Filters written in the query itself (e.g. `Country Name in [...]`) get no icon or `✕`.
- **A query that does not parse says so in the query editor's title.** The Dimensions and Measures / Metrics pickers mark (`✓`) what the query can still take, which needs a parsed query; with one that did not parse they silently showed no marks, which read as "nothing can be added". The editor's title now reads `Query (YAML) · does not parse at line 5` in orange until the query parses again, and the pickers show no marks meanwhile.
- **Filters listed in another order share a result-cache entry.** The cache found an entry by the compiled SQL, which keeps the filters in the order given, so `Client = A AND Product = B` and `Product = B AND Client = A` were two entries for the same rows. In the UI each click-to-filter adds its filter at the end of `where`, so clicking the same two values the other way round ran the query on the database again. The key is now built from the compiled SQL with its conditions joined by AND in a fixed order, rendered by the same dialect. Nothing else moves, so two queries share an entry only when they read the same rows. The SQL that runs is unchanged, except that the CTEs of a period-over-period metric list the query's filters in that order. Filters on data objects that only the filters bring into the query are joined in the order given, so those still make two entries. REST, pgwire, Flight SQL and `/v1/oneshot/batch` key the same way; a query reading several data sources is keyed on its SQL as written. See [When two queries share an entry](docs/guide/result-cache.md#when-two-queries-share-an-entry).
- **Every REST endpoint names the access it needs, and a session belongs to whoever created it.** This prepares OpenID Connect sign-in. Each `/v1` endpoint requires `obsl:read`, `obsl:write` (load or remove a model, close a session, `/v1/oneshot/batch`) or `obsl:admin` (the result and compilation caches). A session created by a signed-in user is visible only to that user and to admins; anyone else gets 404, as for a session that does not exist, and `GET /v1/sessions` and the top-level shortcuts only see the caller's own sessions. API keys and `AUTH_MODE=none` hold all three scopes and create shared sessions, so nothing changes for them.

### Removed

- **`AUTH_ENABLED`, `FLIGHT_AUTH_MODE` and `FLIGHT_API_TOKEN`.** Deprecated since v2.12.0. A deployment that still sets one to turn authentication on (`AUTH_ENABLED=true`, `FLIGHT_AUTH_MODE=token`, any `FLIGHT_API_TOKEN`) now refuses to start and names it, rather than starting without the authentication it asked for: set `AUTH_MODE=api_key`, and move a Flight token into `API_KEYS`. `FLIGHT_AUTH_MODE=none` is ignored. `GET /v1/settings` reports Flight's `auth_mode` as the `AUTH_MODE` it follows (`none`, `api_key`, `oidc`); it reported `FLIGHT_AUTH_MODE` before, so `none` even with `AUTH_MODE=api_key`.

### Fixed

- **With `AUTH_MODE=oidc`, Arrow Flight SQL and the Postgres wire protocol require an API key.** Both checked for `api_key` alone, so any other mode, `oidc` included, would have left them open to every client. `oidc` refused to start until now, so no deployment was exposed.
- **A pick from the UI's Dimensions, Measures / Metrics or Columns picker adds to the key the query already has.** The picker found that key by its text, exactly `  measures:` with list items four spaces in. A key at another indentation got a second `measures:` block, and after a click-to-filter or a sort in Query Results, which write list items at the key's own indentation, the next pick wrote a query that no longer parsed. The picker now edits the query as parsed YAML: it keeps the editor's indentation, comments and inline lists, and does not add an item the query already selects. A query that does not parse is left as it is, with a warning naming the line to fix.

## [3.1.1] - 2026-11-19

### Added

- **A Model dropdown in the UI when `MODEL_FILES` loads more than one model.** It leads the SQL Compiler's settings row and lists `GET /v1/models`; picking one loads it into the read-only editor and starts the query box with the model's first example query (or an empty `select` for the pickers). The UI works on each curated model in its own protected session, as BI tools do with the Flight `database` field, so it creates no session of its own and uploads nothing. The choice is remembered in the browser. In curated mode the API Base URL field is hidden: the UI's sessions are on its own API.
- **`GET /v1/models/{name}`: one pre-loaded model with its `model_id` and the YAML it was loaded from.** `GET /v1/models` lists names and counts only, and `/v1/settings.model_yaml` is set only for a single model, so with several there was no way to read a curated model's YAML. 404 for any other name, including a user's own session.

### Fixed

- **The UI works with several `MODEL_FILES` models.** It showed the bundled starter model and every action failed with `403 Single-model mode: model upload is disabled`, because a new user session is seeded only when exactly one model is loaded.
- **The UI inside the API (`/ui`) shows the curated model, not the starter.** The settings passed to the embedded UI carry no model YAML, so with one `MODEL_FILES` model that was not the bundled starter the editor showed the starter while queries ran against the real model. The UI now fetches the model when the page loads.
- **The SQL Compiler's settings row keeps every control on the page.** Every input in the row had a 360px minimum, meant for the API URL but also applied to the Jump to and SQL Dialect dropdowns, and the row did not wrap: at 1300px the API URL was cut off and Export as OSI and OBSL were off the page. The dropdowns now keep their own widths, and a row that does not fit wraps.
- **The UI no longer stops working after ten model edits.** Each edit in the model editor uploads the YAML as a new model, and the earlier versions stayed in the UI's API session. The eleventh version in one session was refused with `429 Maximum models per session reached (10)` and every action failed until the page was reloaded. When the session is full the UI now continues in a new session, as it already did when a session had expired. The full session is left to expire rather than emptied, because two UI actions can run at once and each may still be using one of its models. A model the API rejects also keeps the session it was sent to: the UI used to drop a session it had just created (on a new page, or for a full or expired session) when the upload failed validation, so each retry of an invalid model created another session, until the session-creation rate limit (10 a minute) refused the corrected one. `tests/integration/test_ui_session_models.py` drives the UI's client against the API: edits past a cap of two, two concurrent actions that each upload a different version, and twelve rejected attempts followed by the corrected model.
- **The UI continues after its API session expired, instead of failing the first action after a pause.** An expired session answers its first request with `410 Gone` (the API drops it then, and answers 404 afterwards), and the UI recovered only from 404. By default Cloud Run gives an instance CPU only while it handles a request, so the cleanup sweep rarely drops a session before that request: after 30 idle minutes the next compile, execute, ER diagram, SPARQL, business-rules or model lookup showed `HTTP 410 ... has expired`, the RDF graph came back empty, an edited model raised an error, and the Settings tab showed a 404 error. Every action now continues in a new session on either answer, and the Settings tab falls back to the API's settings. A missing rule or artefact still reports its own 404. The API docs said expired sessions answer 410 rather than 404; they answer 410 once. `tests/integration/test_ui_session_models.py` expires the session before each of the eight actions; `tests/ui` does it in a browser, Settings tab included.
- **The UI shows the API's model when the API was still starting as the UI started.** The UI asks the API what it serves once, when its process starts, and gave up after about 20 seconds. On Cloud Run a scaled-down API starts on its first request, and on the demo that once took 95 seconds: every page then showed `# API unreachable` until the UI restarted. Reloading did not help, although the message said it would. At startup the UI now waits up to two minutes while the API is starting (a timeout, 429 or 5xx; a refused connection, with no API running, still fails fast). A page built without an answer asks the API again on each load and sets itself up for what it serves: a curated model read-only, with the API Base URL and Import OSI hidden, or the starter model for self-service.
- **Models uploaded into one session at the same time no longer fail with `YAML_PARSE_ERROR`.** A session's model store parsed every upload with one YAML parser, which keeps the state of the document it is reading, and the API runs uploads in parallel: two at once mixed their documents up and rejected valid models. Each load now gets its own parser. `tests/unit/test_parser.py` loads two models from eight threads with one loader.
- **A query over several facts grouped by a dimension read `via` a fact none of them reaches is refused, instead of failing in the database.** With Total Sales and Total Returns, `Purchase Department` (`via: Purchases`) has no value in either part of the `UNION ALL`, and each part left it out, so the SQL named a column the union does not have: DuckDB answered `Binder Error: Column "Purchase Department" referenced that exists in the SELECT clause`, and the other dialects returned NULL for it on every row. It is now refused with `UNREACHABLE_REQUIRED_OBJECT`, naming the dimension and its `via` object, as the same query over one fact always was. Beside a measure of a fact that reaches it (Total Purchases), the dimension is grouped as before. The composables check (`/composables`, and the UI's highlighting in the dimension and measure pickers) no longer offers such a dimension when nothing that reaches the query's facts reaches the `via` object, nor a measure that would leave one in that state. Where something does, it is still offered, and the compiler decides (see the composability guide).

### Docs

- **CHANGELOG.md holds the releases from 3.0.0 on; earlier ones are in `CHANGELOG-archive.md`.** GitHub formats a Markdown file only up to about 250 KB, so at 568 KB it showed CHANGELOG.md as source; CHANGELOG.md is now 165 KB, and the archive (409 KB) is shown as source. `CHANGELOG-versions.md`, a table with one row per release that nothing linked to, is removed: its rows for 0.1.0 to 0.8.0, which have no changelog entries, moved to the archive, and `scripts/release.sh` no longer asks for a row there.

## [3.1.0] - 2026-11-17

### Upgrading from 3.0

3.1.0 reads [files and lakehouse tables](https://ralforion.com/orionbelt-semantic-layer/guide/files-and-lakehouse/) in a DuckDB data source, can run a DuckDB source's queries on [DuckDB workers](https://ralforion.com/orionbelt-semantic-layer/guide/duckdb-workers/), inspects a data source's catalog, and reads and writes Apache Ossie 0.3 (osi-orionbelt 0.7.0). It also changes some answers a 3.0 client gets. Each change is described in full below; these are the ones to check before upgrading.

| What changes | What to do |
|---|---|
| A DuckDB data source reads only its own database. A view over Parquet or CSV files in the database file, or a model naming files in `code`, is refused with DuckDB's `Permission Error` | List the files' directory in `DB_<NAME>_DUCKDB_ALLOWED_PATHS` (or `DUCKDB_ALLOWED_PATHS`); `*` reads anything, as before |
| A DuckDB data source's memory limit is half the memory, not DuckDB's 80% | `DUCKDB_MEMORY_LIMIT=80%` restores DuckDB's default |
| On Databricks, `date_diff` over timestamps counts the boundaries crossed, as on the other seven engines: 23:00 to 01:00 the next morning is 1 day, not 0. Rolling windows and cumulative as-of filters over a timestamp take the rows they take elsewhere | Nothing, unless a report relied on Databricks' whole-unit count |
| A measure over two facts, such as `SUM(orders.amount - returns.amount)`, counts a fact with no rows as 0, so a customer with orders and no returns adds its orders. `AVG`, `MIN` and `MAX` include anchor rows that have only one of the facts | Nothing: totals of such measures now count the rows that dropped out (Apache Ossie's compliance example: 615, was 275) |
| The Ossie export writes `version: "0.3.0.dev0"` and `nonportable_extensions`, whose `data` is an object | A consumer of the export's `custom_extensions` reads `nonportable_extensions` |

### Added

- **Schema inspection: what a data source holds, from its catalog.** `GET /v1/datasources/{name}/schemas` lists a source's schemas without the engine's own, and `GET /v1/datasources/{name}/schemas/{schema}/tables` describes a schema's tables and views: columns with the engine's type, position (from 1 on every engine, Databricks counting from 0 included), nullability and comment, the primary key and foreign keys (composite keys paired column by column), and with `?view_definitions=true` each view's SQL; `?table=` narrows it to some tables, `?views=false` leaves views out. Ported from OrionBelt Analytics' drivers, without SQLAlchemy: each engine's catalog (`pg_catalog` on PostgreSQL, `duckdb_*()` on DuckDB, `system.*` on ClickHouse, `information_schema` elsewhere, `SHOW ... KEYS` for Snowflake's keys) is queried over the same pooled connections queries run on, one statement per kind of fact rather than per table. Keys or view bodies the catalog will not show the user add a warning instead of failing the request. Requires `QUERY_EXECUTE=true`. Checked on all eight engines with `scripts/probe_schema_inspection.py`, which builds a schema with composite keys, comments and a view on each and drops it again; ClickHouse also by a Docker test (`-m docker`).

- **`current_timestamp()` and `current_time()` in OBML expressions, on each engine's own clock and in the model's time zone.** The catalog left `current_timestamp` out because the engines disagree on what theirs is: an instant on PostgreSQL, DuckDB, Snowflake, BigQuery and Databricks, the session's wall clock on MySQL, UTC's on Dremio. It now has a stated meaning: a timestamp without a time zone, the wall clock in `settings.queryTimezone` where the model sets one, read from the current instant as the model's timestamp columns are, so `{[Orders].[Placed At]} <= current_timestamp()` compares one zone's clock on both sides; without `queryTimezone`, the session's local clock, as `current_date()` is the session's date. Each engine renders it with its own functions (`CURRENT_TIMESTAMP AT TIME ZONE`, BigQuery's `CURRENT_DATETIME(zone)`, Snowflake's `CONVERT_TIMEZONE` as `TIMESTAMP_NTZ`, ClickHouse's `toTimeZone(now64(6), zone)`, Databricks' `convert_timezone`, MySQL's `CONVERT_TZ(UTC_TIMESTAMP(6), ...)`, Dremio's `CONVERT_TIMEZONE`). `current_time()` is its time of day, `TIME(6)` on MySQL and `'HH:MM:SS'` text on ClickHouse and Databricks, where OBML's `time` is text. `test_current_clock_exec.py` runs both on all eight engines in a zone at UTC+05:45 against this host's clock, and without a zone; a query reading the clock is never served from the result cache (`now64`, `CURRENT_DATETIME` and `current_localtimestamp` joined the clock reads it looks for).

- **OBML expressions take `%`, `||`, `ILIKE` and `IS [NOT] DISTINCT FROM`.** Four standard SQL operators the expression parser refused, so a computed column, measure expression or metric formula using one stopped the whole model loading (`INVALID_COLUMN_EXPRESSION`, `INVALID_MEASURE_EXPRESSION`). Apache Ossie's expression language has all four, so they also come with imported models. Each is written in forms every engine runs: `a % b` as the portable catalog's `mod` (BigQuery has no `%`), `a || b` as its `concat`, which keeps the rule that a NULL operand makes the result NULL (MySQL reads `||` as OR, and PostgreSQL's, DuckDB's and Dremio's `CONCAT` skip NULLs), `[NOT] ILIKE 'pattern'` as the case-insensitive match a query filter's `ilike` uses (`LOWER` of both sides on BigQuery and MySQL), and `IS [NOT] DISTINCT FROM` as the engine's own NULL-safe comparison, `<=>` on MySQL, which has no such operator, so each operand is evaluated once. `%` binds like `*`, and `||` looser than `+`. `tests/integration/drift/vendor_exec/test_expression_operators_exec.py` runs each on all eight engines.

- **Prometheus metrics for OrionBelt itself: requests, queries, caches and sessions.** Beside the DuckDB worker pools' metrics, `/metrics` now reports the REST API's requests (`obsl_http_requests_total` and `obsl_http_request_duration_seconds`, by method, `other` for one HTTP does not define, route template such as `/v1/sessions/{session_id}/query/execute`, and status, so no label takes a value a client chooses and the series do not grow with sessions), the queries run on a database (`obsl_queries_total` and `obsl_query_duration_seconds`, by surface `rest`, `pgwire`, `flight` or `other`, dialect, data source and outcome `ok`, `error` or `unavailable`; a result served from the cache runs none, and a federated query counts each leg on its own source), and, read at each scrape, the build (`obsl_build_info`), the sessions open, and the result cache's and the compilation cache's entries, size and lookups by result. Still off by default: then no request or query is counted and the Prometheus client is not loaded (a test checks it in a fresh process). A query keeps the surface it came in through across the executor threads it runs in: REST's two hand-offs to a thread pool now run in a copy of the request's context, which a test shows was lost before (the query counted as `other`). A scrape reads the result cache on its own thread, never on the API's event loop, and the file cache's statistics no longer wait for the lock its other operations take, nor write: its hit and miss counts are kept in memory, and its entries are read on a DuckDB connection of their own (a test reads them while another thread holds the lock), so `GET /v1/cache/stats` no longer waits for them either. New reference page: Metrics.

- **Prometheus metrics, off unless `METRICS_ENABLED`.** `/metrics` answers on a port of its own (`METRICS_HOST`, `METRICS_PORT`, `0.0.0.0:9090`), not the API's, so it stays off a public API unless that port is published. For each DuckDB source on Hardcharger workers and each worker (labelled `source` and `worker`, the `host:port` the source lists), read at each scrape: `obsl_duckdb_worker_up`, `obsl_duckdb_worker_connections` by state (`in_use`, `idle`, `opening`), `obsl_duckdb_worker_statements_total` (statements the worker ran, a session's setup as one, those that failed or that the pool ended included), `obsl_duckdb_worker_retries_total` by reason (`unreachable`, `connect_timeout`, `session_not_found`, `rate_limited`, `server_draining`) and `obsl_duckdb_worker_statements_ended_total` by reason (`deadline`, `unresponsive`); with them the process's CPU, memory, open files and garbage collection. New dependency: `prometheus-client` (pure Python, none of its own), imported only when the metrics are on. `obsl.env.example` turns them on in a commented line, and the DuckDB Workers guide has a scrape configuration for them and the workers' own (port 9091).

- **DuckDB sources on Hardcharger workers: sturdier, and their driver in the `-flight` image.** `ralforion/orionbelt-semantic-layer-flight` is built with the `hardcharger` extra; the API image is not. The pools of such sources start with the server, so each worker's health is known before the first query. Health checks run in a thread of their own: a silent worker's checks wait up to 2 s each, and held up the statements' deadlines while they shared one (in a test with a stand-in worker, a 0.4 s deadline ended after 2.1 s). The examples set DuckDB's HTTP limits (`SET GLOBAL http_timeout = 10; SET GLOBAL http_retries = 2`), in the workers' init SQL and in `obsl.env.example`'s in-process block: measured with the object store stopped, an Iceberg query failed after 120 s with DuckDB's defaults (30 s, 3 retries), since the catalog hung waiting for the store too, and after 31 s with the limits. `SET GLOBAL` is needed: a plain `SET` lasts for the setup's own connection only. `tests/docker/test_compose.sh` (63 checks) now also stops a worker in the middle of a query: killed, the query failed within 1 s; paused, so that its connections stay open and nothing answers, the pool's health checks ended it within 20 s; neither returned a short result, and the next queries went to the other worker. `tests/integration/test_duckdb_pool_hardcharger.py` runs two sources with their own users on the same workers: each reads its own files and is refused the other's.

- **A DuckDB data source's queries can run on Hardcharger workers** (`DB_<NAME>_DUCKDB_BACKEND=hardcharger`), DuckDB servers beside OrionBelt that stream Arrow, for a lake source whose load needs more than one process. Off by default: a source without the setting, and every other source, runs as before, and nothing of the workers' code runs for it (no driver import, thread or connection). The source names its workers (`HARDCHARGER_WORKERS`, `hardcharger://host[:port]`, TLS unless `?tls=false`, `HARDCHARGER_TLS_ROOT_CERTS` for a private CA) and the user their init SQL creates for it (`HARDCHARGER_USER`, `HARDCHARGER_PASSWORD`); the SQL stays DuckDB's, so REST, the Postgres wire, Flight SQL, `EXPLAIN`, the session time zone, online validation, value search and a federated query's legs run there alike, and the results equal those in process (types included). The backend, the workers and the user are part of the source's identity, so two sources on other workers or users share no connection and no cached result. Each query goes to the healthy worker with the fewest connections in use (at most `HARDCHARGER_CONNECTIONS_PER_WORKER`, default 4) and holds that connection until its result is read. What never ran is run again, on another worker where one is free: a worker that cannot be reached, a session it no longer has (`session_not_found`, after a restart or an idle eviction), a full statement queue (HTTP 429) and a worker shutting down (`server_draining`); anything else is the query's own failure. The driver's own reconnect is off, since it would carry on in a session without `DUCKDB_CONNECTION_SQL`: a lost session is replaced by one that runs those statements again. Every statement carries a timeout on the worker (`HARDCHARGER_QUERY_TIMEOUT_SECONDS`, 120), the connection statements included, which are retried like a query, and opening a connection gives up after `HARDCHARGER_CONNECT_TIMEOUT_SECONDS` (10), since the driver waits forever on a worker that keeps its port open without answering; a connect given up on counts against the worker's connections until it comes back, so such a worker is not handed one more for each query. A worker is checked every `HARDCHARGER_HEALTH_INTERVAL_SECONDS` (5): one that does not answer `serving` takes no queries until it does, one shutting down finishes what runs on it, and the queries on one that does not answer twice in a row are ended, as is a statement unanswered 10 s past its timeout. Measured on a paused worker, closing the cursor from another thread ends a hung read at once and a hung `execute` within about 5 s, where a cancel waits on the same unresponsive server. The settings that set up DuckDB in process (`DUCKDB_INIT_SQL`, `DUCKDB_ALLOWED_PATHS`, the memory, thread and spill settings, `DUCKDB_DATABASE`) are refused for such a source rather than ignored, since the workers' init SQL and the user's location grants set those up, and a source that cannot run stops the server at startup with a message naming it. The driver is the new `hardcharger` extra (`adbc-driver-hardcharger` 2.5); the Dockerfile's `OB_EXTRA` takes several extras, and `deploy/compose/compose.pool.yml` builds OrionBelt with it and gives the workers time to finish their statements when stopped. `obsl.env.example` holds the source's settings in a block to uncomment. New guide: DuckDB Workers. Tested against a stand-in driver (62 tests), against two real workers (`tests/integration/test_duckdb_pool_hardcharger.py`, `pytest -m docker`, a session the worker evicted included), and in `tests/docker/test_compose.sh` (53 checks), where with one worker stopped every REST query was answered by the other.

- **A Docker Compose setup, with a local lake and DuckDB workers on request** (`deploy/compose/`). `compose.yml` runs OBSL alone, built from the checkout or from a published image (`OBSL_IMAGE`), with its settings in `obsl.env` as for `docker run --env-file`, models and files mounted at `/models` and `/data`, and federation's spill files on a volume. As shipped, it starts with the example model built into the image. `COMPOSE_PROFILES=lake` adds a local lake for development: an S3 endpoint (Versity S3 Gateway, since MinIO's images are no longer pullable from Docker Hub or Quay) and the Apache Iceberg project's REST catalog. `obsl.env.example` has a block, commented out, for a source that reads the lake in process, to uncomment with the profile. `compose.pool.yml` adds two DuckDB workers (Hardcharger 2.12.1, pinned by digest) for lake sources: named services that publish no ports, each running the same init SQL from a Compose secret (one user per OBSL source with the locations it may read; a block for the lake's extensions, storage and catalog secrets and `ATTACH`, again to uncomment with the profile) and keeping its own users. OBSL does not send queries to the workers yet. `tests/docker/test_compose.sh` runs the setups with the shipped examples as they are and with their lake blocks (47 checks), including a source's user refused outside its grants and what a worker does when the catalog or object storage is down: a worker whose catalog is down at its start exits and is restarted until the catalog answers, so with the local lake the workers wait for its catalog; a catalog lost while running fails Iceberg queries at once and recovers on its own; object storage lost makes Iceberg queries wait until the statement timeout.

- **A DuckDB data source reads files and Iceberg tables in place, within a memory limit you set.** A data object's `code` can name Parquet, CSV or JSON files by path or glob, on disk or in S3 (`schema: ""`), and Iceberg tables are read through a REST catalog attached by the source's new setup statements, `DUCKDB_INIT_SQL`: statements DuckDB runs once for each instance of the source, on REST, the Postgres wire and Flight SQL alike (`CREATE SECRET`, `ATTACH ... (TYPE iceberg)`), with `DUCKDB_CONNECTION_SQL` for what lasts one connection (`SET search_path`). A source without a database file runs its setup once while the server runs, so a catalog's OAuth2 secret asks its token server once for all queries, and DuckDB renews the token as it expires (measured: before `expires_in`, and on a `401` for a token without one or revoked early; a fixed bearer token fails with the `401`). They are never shown, an error names the variable rather than repeating them, and they count toward the source's identity, so the result cache keeps their results apart; they run for one connection of an instance at a time, since two `CREATE OR REPLACE VIEW`s at once conflict in DuckDB's catalog. A source without a database file (`:memory:`) refused to start, opened read-only; it now keeps one DuckDB instance, and its queries share one memory limit and what the setup attached (measured on a local REST catalog: 11 ms a query against 55 ms when each query attached the catalog anew). New settings per source: `DUCKDB_MEMORY_LIMIT`, `DUCKDB_THREADS`, `DUCKDB_SPILL_DIR` and `DUCKDB_SPILL_MAX_MB` (the cap holds in DuckDB's default directory too); they count toward the source's fingerprint, so a connection pool hands each source connections with its own settings. Unset, a source without a database file spills under the system's temp directory, unless that is in memory; DuckDB's own default, `.tmp` in the working directory, cannot be written in the Docker image. Measured in a 1 GB container, four queries at once each grouping 24 million Parquet rows: with DuckDB's defaults the server was killed for memory after 11 s; with `DUCKDB_MEMORY_LIMIT=500MB` all four answered in about 83 s, spilling. The Docker images let DuckDB download its extensions on first use (`/app/.duckdb` was not writable), and `--build-arg DUCKDB_EXTENSIONS="httpfs iceberg avro"` builds them in (about 105 MB). `ob-duckdb`'s `connect()` takes `init_sql`, run on the connection and on every cursor. Tested against Apache Iceberg's REST catalog with MinIO (`tests/integration/test_iceberg_rest_source.py`, `pytest -m docker`). New guide: Files and Lakehouse Tables.

- **Online validation reads a sample of the rows, on request.** `obsl validate --sample 1000` or `--sample 1%`, and `?sample=` on both validate endpoints (each implies the online check), read a sample of each data object that passed the zero-row check, for what only a value shows. A count reads the first that many rows; a percent draws about that share row by row (`WHERE <random> < 0.01`, written per engine), at most 1000 rows, on tables and views alike. On BigQuery a percent reads blocks of a table (`TABLESAMPLE SYSTEM`), the only form billed for less than the whole table: measured on a 7.3 GB column, 72.8 MB for 1 percent against 7.3 GB for `LIMIT 1000`; a view falls back to the row-by-row form. Findings are warnings and leave the model valid: `DATASOURCE_SAMPLE_FAILED` for a value a computed column or nested field cannot compute (`{Name} * 2` on Snowflake, Dremio and Databricks plans and fails only on a row), named per column where it fails on its own, and `DATASOURCE_SAMPLE_ALL_NULL` for a nested field NULL on every sampled element, which is what a field the elements lack reads as on Snowflake and MySQL. Native sampling was measured on all eight engines first and not taken: MySQL and Dremio have none, PostgreSQL and BigQuery refuse it on views, ClickHouse ignores it on a view without a word, and block sampling returned no rows from a 10,000-row table on DuckDB. `test_datasource_probe_exec.py` runs the sample on seven engines.

- **Online validation checks computed columns and nested data objects.** `obsl validate --online` and `POST .../validate?online=true` read only the plain columns of each data object: a computed column's `expression` was never sent to the database, and a `nestedIn` data object was skipped. Each data object is now read the way a compiled query reads it, in one `SELECT ... LIMIT 0` built from the compiler's own pieces: a computed column as its expression, written for that database, and a nested data object's fields unnested from its parent's array column, on the parent's data source (Dremio, which cannot unnest in a FROM clause, reads the object's `code` table, as its queries do). A model that matches its database still costs one round trip per data object. When the statement fails, each computed column and nested field is read on its own to name the one that failed. Two new codes: `DATASOURCE_EXPRESSION_FAILED` (at the column's `expression`) and `DATASOURCE_UNNEST_FAILED` (at `nestedIn.column`); a nested field the elements lack is `DATASOURCE_COLUMN_MISSING`, and a computed column returning another type than it declares is `DATASOURCE_TYPE_MISMATCH`. `test_datasource_probe_exec.py` runs the check on seven engines. A missing nested field is reported on DuckDB, PostgreSQL, ClickHouse, BigQuery and Databricks; on Snowflake and MySQL it reads as NULL and cannot be seen. A computed column reading another data object is not checked. A `boolean` that MySQL (no boolean type) or a ClickHouse comparison (`UInt8`) returns as an integer is not reported as a type mismatch, for plain and computed columns alike: a MySQL `BOOLEAN` column, stored as `TINYINT(1)`, was reported before.

- **A measure that cannot be grouped by a query dimension says so (`DIMENSION_NOT_APPLIED`).** In a query over several facts, a fact that cannot reach a dimension's data object put all its values in the row where that dimension is NULL, and showed 0 or NULL in every other row without a word: revenue and ticket count by region, where tickets join nothing, read like no region had tickets. The new warning names the measures and the dimensions. The values stay where they were, so the rows still add up to the total. The OSI guide has a new section, Querying an Ossie model, listing where OBSL answers a query the Apache Ossie query drafts refuse or answer with other rows, and what to do for Ossie's answer.

### Changed

- **The Ossie converter reads and writes Apache Ossie 0.3.0.dev0 (osi-orionbelt 0.7.0).** Upstream moved to 0.3.0.dev0, and the import read none of its new shapes: Ossie's own compliance models converted to a model with no measures, and the SCOTT model did not load. The import now reads `expression: {sql: ...}` (the portable `OSSIE_SQL_2026` form, ahead of an `OSSIE_SQL_2026` entry in `dialects`), metrics declared on a dataset (as measures with qualified references, `COUNT(*)` counting the dataset's primary key), `AGG(dataset.metric)` in a model-level metric, and `nonportable_extensions`; 0.2.0.dev0 and 0.1.x documents still load, and a document is checked against the schema of the version it declares. The export writes `version: "0.3.0.dev0"` and `nonportable_extensions` with JSON object data, and a field's expression also in `OSSIE_SQL_2026` where it is in that language (a field imported from `OSSIE_SQL_2026` came back as `ANSI_SQL` only). Constructs OBML cannot take are kept out with a warning and preserved for the round trip, instead of being written as OBML that stopped the whole model from loading: a model-level `COUNT(*)` (no dataset to count), a field read outside every aggregate, a `CAST` to a type other than `double` or `decimal(p, s)`, and a relationship from a dataset to itself (OBML refuses a join cycle). `CAST(x AS DOUBLE)` is written as OBML's `cast(x, 'double')`, which OBML parses. A field marked `dimension` becomes a dimension when it is also a join key. **Upgrading:** a consumer that reads the export's `custom_extensions` reads `nonportable_extensions`, whose `data` is an object, not a JSON string.

- **Every field of an imported Ossie model is a dimension.** Ossie lets a query group by any field; its `dimension` marker only adds `is_time`. The import made a dimension of marked fields only, so Ossie's own compliance models, which mark none, had nothing to group by: revenue by customer region could not be asked. Each field is now a dimension named as the field, a marked one first, so it keeps its name when a field of another dataset has the same one (that one is named with its dataset, `returns amount`, with a warning). A field named like a measure, a metric or a count measure is named with its dataset too, since OBML refuses a model where two of them share a name (a marked one stopped the whole model loading), and a field OBML cannot read becomes a dimension only when marked. The export writes no `dimension` marker on a field that had none, and a field an OBML export wrote is a dimension only where the OBML model had one, so a round trip either way adds none. With this, four grouped cases of Ossie's compliance suites give the suites' results on DuckDB (wide_table a01, a05, a07; query a02).

- **A DuckDB data source reads only its own database, unless `DUCKDB_ALLOWED_PATHS` lists more.** A data object's `code` can name a file, so a model could read any file the server could: a configuration or key file with a `.json`, `.csv` or `.parquet` name. A source now reads its database alone; `DB_<NAME>_DUCKDB_ALLOWED_PATHS` (or `DUCKDB_ALLOWED_PATHS`) lists the directories, files and URL prefixes (an S3 bucket, an Iceberg catalog's REST endpoint) its queries may also read, and `*` keeps the old behavior. The setup statements run before the limit is set, so they can still load extensions and attach a catalog. A path left out is refused with DuckDB's `Permission Error`, which names the setting. DuckDB enforces it (`allowed_directories`, `allowed_paths`, `enable_external_access = false`): a directory admits nothing beside it, `..` does not climb out, and the limit cannot be lifted while the instance runs. A MotherDuck database is not limited unless the setting is given. Sources reading one database file at once share DuckDB's instance of it and its limit, so the first source to open a file (by its real path, however spelled) decides its paths until the server restarts, and a source of the file with other paths is refused rather than reading with another source's paths or cutting off one without a limit. **Upgrading:** a DuckDB file holding views over Parquet or CSV files, or a model naming files in `code`, needs the files' directory listed.

- **A DuckDB data source's memory limit is half the memory unless set.** DuckDB's own default, 80% of the memory it sees, leaves the server around it no room: in a 1 GB container four concurrent queries got the server killed for memory at 80%, and finished by spilling in about 68 s at 50%. `DUCKDB_MEMORY_LIMIT` sets another (`80%` restores DuckDB's).

- **Apache Ossie's functions that OBML's catalog has under another name or form import as that function (osi-orionbelt 0.7.0).** Ossie's own `DATEADD(day, 7, d)` and `DATEDIFF(day, a, b)` were preserved as metrics OBML could not represent: sqlglot's default grammar read the bare `day` as a column, and a dataset-scoped metric qualified it like one (`orders.day`). They are now read in Ossie's argument order and import as OBML's `date_add` and `date_diff`, which count as Ossie's and Snowflake's do (boundaries crossed). Databricks' two-argument `DATEDIFF(end, start)` is the days between the dates, also OBML's `date_diff`; its `DATEDIFF(unit, start, end)` and `TIMESTAMPDIFF` count whole units elapsed, and import as `date_diff` too, one meaning on every engine, with a `RECOUNTED` warning that the numbers differ from Databricks' (23:00 to 01:00 the next morning is 0 days there and 1 here, January 31 to February 28 is 0 months there and 1 here). sqlglot parses Databricks' two forms to one node, so the import tells them apart by the arguments written. `YEAR(d)` to `SECOND(d)`, `DATE_PART('year', d)`, `EXTRACT(WEEK ...)` (ISO, as the spec's weeks start on Monday), the ISO day of the week, `DAYOFYEAR`, `TRIM(BOTH ' ' FROM s)` and its LEADING and TRAILING forms, `IFF`, `NVL2`, `ZEROIFNULL`, `NULLIFZERO`, `POSITION(a IN s)`, `CHARINDEX`, `CONTAINS`, `LEFT`, `RIGHT`, `PI`, `DEGREES` and `RADIANS` were passed through as written, to run only on an engine that happens to have them; each is now OBML's catalog form, in a metric or a field. `EXTRACT(DAYOFWEEK ...)`, which engines number from Sunday or from Monday and the spec does not settle, stays preserved. The export writes OBML's `date_add`, `date_diff`, `extract` and `position` in `OSSIE_SQL_2026` as `DATEADD`, `DATEDIFF`, `DATE_PART` and `CHARINDEX`, in a measure and in a metric's formula, and in `ANSI_SQL` as `EXTRACT(YEAR FROM d)` (the ISO day of the week as `ISODOW`), `POSITION(a IN s)`, `DATEADD` and `DATEDIFF` (ANSI SQL has no date difference); `EXTRACT('year', d)` and `POSITION(a, s)` are neither language's forms, and the export's check now says so instead of tagging them. Each form, read alone, imports as the same measure. OBML's `cast(x, 'double')` went out as `CAST(x, 'double')`, which no SQL reads, in both forms; it is now `CAST(x AS DOUBLE)`, which reads back as the same cast. `test_the_ossie_functions_run_as_duckdb_s_own` compares each with DuckDB's own function.

- **Dependencies**: sqlglot 30.31.0, fastapi 0.162.7, typer 0.29.1, pydantic-settings 2.16.3, pymysql 1.2.4; the `ob-flight-extension` and `ob-duckdb` pins rise to 3.1.0, whose DuckDB settings (setup statements, allowed paths, memory, workers) 3.1.0 reads (#806, #807, #808).

### Fixed

- **The Arrow response's envelope carries `federation` and the cache TTL fields, as the JSON response does.** `format=arrow` frames the rows behind a JSON envelope meant to mirror the JSON response without `rows`, but `federation`, `ttl_seconds`, `ttl_source` and `ttl_limiting_table` were set on the JSON response after it was built and never reached the envelope, on a fresh run or a cache hit. A client reading Arrow lost where each leg of a federated query ran, and how long the result is cached. Both surfaces now take the four fields from one place, and a test holds the envelope to the JSON response's fields.

- **`date_diff` and `date_add` answer alike on all eight engines.** Databricks' `date_diff` counted whole days, hours, minutes and seconds on a timestamp where the catalog pins boundaries crossed: 23:00 to 01:00 the next morning was 0 days, 1 on the other seven; both ends are now truncated to the unit first, as they already were for months, quarters and years. Rolling windows and cumulative as-of filters count their days with it, so over a timestamp they now take the same rows on Databricks as on the other engines. BigQuery wrote `date_add('week', n, x)` as `INTERVAL n ISOWEEK`, which it refuses ("Invalid interval datetime field ISOWEEK"); `ISOWEEK` is the numbering its `DATE_DIFF` and `EXTRACT` take, and an interval's week is `WEEK`. Dremio's `div(a, b)` truncated a decimal quotient and stayed a DECIMAL where the catalog promises an integer, so a week difference (a `div` of days) given to `date_add` made `TIMESTAMPADD` refuse its amount; it is now cast to BIGINT. `test_date_arithmetic_exec.py` runs `date_diff` in all eight units and `date_add` at month ends, leap days, across midnight and backwards on all eight engines against the catalog's rules written out; the catalog gains examples for a week, a computed count, timestamps across midnight and a fraction of a second. MySQL and ClickHouse wrote a timestamp literal in whole seconds (`CAST('... 00:00:00.9' AS DATETIME)` rounds up to the next second, `DateTime` drops the fraction), so `date_diff('second', TIMESTAMP '... 00:00:00.9', TIMESTAMP '... 00:00:01.1')` was 0; a literal with a fraction of a second is now `DATETIME(6)` and `DateTime64(6)`, and one without is written as before.

- **An Ossie metric with `FILTER (WHERE ...)` imports, and a model's and a metric's `ai_context` survive a round trip (osi-orionbelt 0.7.0).** Apache Ossie's expression language requires the aggregate `FILTER` clause, but the import preserved every metric using it as one OBML could not represent. It now imports `AGG(x) FILTER (WHERE p)` as the measure of `CASE WHEN p THEN x END`, the rewrite the spec gives for an aggregate that ignores NULLs (`COUNT(*)` counts `CASE WHEN p THEN 1 END`), alone, inside a formula or in a dataset-scoped metric; a group with no matching row keeps its row, with an empty sum and a count of 0. A FILTER over an aggregate not relied on to skip NULLs (`ANY_VALUE`, which keeps them on Databricks, `MODE`, `LISTAGG`), with several arguments or under `OVER` is still preserved. So is any metric whose aggregated expression OBML's expression parser does not read, FILTER or not: an operator it lacks (`LIKE ... ESCAPE`, `ILIKE` against a column, or with a backslash in its pattern, which OBML reads as an escape and Snowflake does not), SQL syntax inside a call (`EXTRACT(DAYOFWEEK FROM d)`, `TRIM(BOTH 'x' FROM s)`), a word it would read as text (`INTERVAL`), or a call to one of OBML's catalog functions with an argument count or unit it refuses (`ROUND(x, 1, 2)`). Imported as a measure, each stopped the whole model loading. `%`, `||`, `ILIKE` with a string pattern and `IS [NOT] DISTINCT FROM`, which OBML expressions take since #802, import as written, in a metric or in a field. `EXTRACT(YEAR FROM d)` (and QUARTER, MONTH, DAY, HOUR, MINUTE, SECOND) becomes OBML's `extract('year', d)`, and `CURRENT_DATE`, `CURRENT_TIMESTAMP` and `CURRENT_TIME` its `current_date()`, `current_timestamp()` and `current_time()`, the session's clock as the source's is, unless the model sets `queryTimezone`. A bare `CURRENT_DATE` was not one: OBML read it as the string `'CURRENT_DATE'`. The converter reads the catalog's arities and units from `obml-functions.json`, written from OrionBelt's catalog by `scripts/refresh_osi_function_table.py` and kept in sync by a test. Every function of Ossie's expression language, inside a metric, now leaves the model loading (81 samples). The export's `OSSIE_SQL_2026` check accepted none of Ossie's four `FILTER` expressions in `compliance/expressions/valid.txt` and three of its malformed ones (`x IN ()`, `SUM(DISTINCT)`, `COUNT(DISTINCT)`); it now agrees with both lists, 66 of 66 and 15 of 15. The model's `ai_context` was dropped, and a metric's kept only its synonyms: the rest (`instructions`, `examples`) is now kept on the OBML model, measure or metric and written back on export, as for datasets and fields. Instructions the export writes itself, for a cumulative metric's grouping, follow the kept ones and are not kept again.

- **The file result cache loses no lookups or writes when threads use it at once.** With `CACHE_BACKEND=file` and Flight SQL on, Flight's handler threads and the API's event loop share the cache's one DuckDB connection to its metadata. A query's rows were read after the cache's lock was let go, and DuckDB 2.0 refuses a call on a connection while another thread's call on it runs (`connection is busy`), so the lookup failed as a miss, or the write was dropped, with a warning in the log. Measured with three threads looking up a stored key and one writing for 5 s: 5,423 of 10,217 lookups missed, and 1,029 of 3,113 writes were kept. Each statement now runs with its rows read under the lock, and each transaction ends under it, its `ROLLBACK` included, which ran after the lock was let go and could end another thread's transaction. The same run then hit on all 4,250 lookups and kept all 2,083 writes, with nothing in the log. Two new tests fail on the old code: threads sharing the cache, and a failed write rolled back under the lock.

- **Flight SQL runs the SQL the compiler wrote, as REST does.** After compiling an OBSQL or OBML query, Flight replaced each quoted data object name in the SQL with the object's `code`, unquoted, a leftover from when it passed client SQL through. A data object reading a file (`code: /data/orders.parquet`) became `FROM "/data/orders.parquet" AS /data/orders.parquet`, which DuckDB refuses, so every such query failed over Flight while REST ran it; and a result column named like a data object (a measure `Orders` on the data object `Orders`, `code: orders`) came back named `orders`, not matching the schema Flight announced. Flight now runs the compiled SQL unchanged, the same SQL REST and the Postgres wire run. The result cache keys a query by its compiled SQL, and Flight keyed the rewritten SQL: it now keys the same SQL REST and the Postgres wire do, and results it cached before are not found again.

- **The weekly Ossie schema check reads upstream's current file, and fails the run when the file is gone.** Upstream Apache Ossie renamed `core-spec/osi-schema.json` to `ossie-schema.json`. The check kept asking for the old name, got HTTP 404, printed "skipping drift check" and passed, so the move to spec `0.3.0.dev0` (the `sql:` expression form, dataset-scoped metrics, `nonportable_extensions`) raised no issue. It now reads `ossie-schema.json`, and exits 2, failing the run, when the file answers 404 or 410, is not a JSON object, or the check fails in a way it does not expect (an uncaught error exited 1, which filed a drift issue with an empty report). A network error, a server error or a response cut short still skips the week. Run today, it reports the drift (`0.2.0.dev0` -> `0.3.0.dev0` and 16 other changes).

- **A large result returned as Arrow costs a quarter of what it did, and less than JSON.** `format=arrow` built the Python rows the JSON shape needs and then never read them, and compressed the Arrow data with gzip level 6, so a 100k-row result took longer as Arrow than as JSON. It now ships the driver's table without building the rows, and the result frame and the result cache use gzip level 3: within 2% of the size at a fifth of the time (on 2.3 MB of Arrow, 13.7 ms for 313 kB against 69.7 ms for 307 kB). Measured through the REST API on a 100k-row DuckDB result: 27.9 queries a second (p50 36 ms) against 6.4 (132 ms) for one client, and 54.1 against 7.2 for eight, where JSON answers 10.0 and 12.2. The frame and the cache entries keep their format, plain gzip over uncompressed Arrow IPC, so every reader, and every entry written before, still reads them.

- **Measures anchored on different data objects can be asked together.** A measure over two facts runs on its anchor's rows: `SUM(orders.amount - returns.amount)` once per customer by default, once per order with `anchor: Orders`. Asked in one query, the two were planned as one star rooted at orders, which joined the per-customer measure's pre-aggregated facts on the customers table before joining it, and the database refused the SQL (`Referenced table "Customers" not found`). Two or more anchors now get a union leg each, as independent facts do, and each column returns what the measure returns alone, also by group, filtered, ordered, and in a metric over both. Tested on all eight engines.

- **The `dataSource` description says a query across sources is federated.** The OBML model's field description and the JSON schema (`schema/obml-schema.json`, and its copy in osi-orionbelt) still said a query reading data objects of more than one data source "is refused until federation ships", in the release that ships federation. They now say such a query runs as a federated query: one query per source, combined in DuckDB. osi-orionbelt 0.6.2 carries the schema copy.

- **A measure over two facts counts a fact with no rows as 0, so its total adds up.** A measure such as `SUM(orders.amount - returns.amount)` sums each fact per customer, the data object both join to, and evaluates per customer. A customer with orders and no returns had no returns sum, read as NULL, and the whole term dropped out: the Apache Ossie compliance example returned 275 where the facts hold 650 ordered and 35 returned. Each fact's sum now reads 0 where the fact has no rows, and the total is 615. A customer with no rows in any of the facts still adds NULL, so a group without fact rows is NULL, as any SUM over no rows is. The same holds with `anchor:` on one of the facts: an order without returns counts its amount. `AVG`, `MIN` and `MAX` now include anchor rows that have only one of the facts. Tested on all eight engines.

- **An Ossie field computed by an expression is queryable.** The import wrote the field's SQL into the column's `code`, which OBML quotes as one column name: `amount_cents / 100.0` compiled to `"orders"."amount_cents / 100.0"`, a column no table has, on every engine. Such a field is now an OBML computed column, `{amount_cents} / 100.0`, over a sibling whose `code` is the source column: a field computing exactly that column, or a column the import adds for it (the export leaves it out unless the model uses it). `CASE`, comparisons, `IN`, `BETWEEN`, `LIKE`, `IS NULL`, function calls and `CAST(x AS DOUBLE)` (as `cast(x, 'double')`) are converted; an expression OBML cannot parse (`||`, `EXTRACT(... FROM ...)`) is kept with a `LOSSY` warning. The export writes the field's SQL back, or, after an edit, the computed column with each sibling written as its column. osi-orionbelt 0.7.0.

### Docs

- **Querying an Ossie model: ambiguous join paths and dimension-only queries.** The OSI guide's table of where OBSL answers a query the Apache Ossie drafts refuse gains three cases, measured on DuckDB with Ossie's `stores` fixtures: a dimension reachable by a direct and a longer route (OBSL takes the direct one; `via:` reads the other), the same with a filter on it, and a query with dimensions and no metric (the pairs that occur together in the fact). Routes of equal length are refused, as before (#801).

- **pgwire TLS: which certificate to deploy, and *certificate verify failed* with `require`.** The BI tools guide says which server certificate asks what of the users (one from a public CA for the name they connect to asks nothing; a company CA's or a self-signed one has to reach every client as `sslrootcert`), how to connect with `sslmode=verify-full`, and why `require` fails with "certificate verify failed" for a user who keeps a `~/.postgresql/root.crt` for another database: libpq then checks the server against it, as `verify-ca` would. Its DBeaver and Metabase steps still said OrionBelt ships no TLS and to turn SSL off.

- **DuckDB Workers: when they pay off, and how to size them.** Measured on one host with 10 CPUs and 5 GB for OrionBelt and its workers: one OrionBelt process answers 250 to 290 small queries a second over REST whether DuckDB runs inside it or on 1, 2 or 4 workers, so on one host workers add no throughput, and two OrionBelt processes answered the most (478 lookups a second against 291). The guide now says what workers are for (keeping DuckDB's memory apart from OrionBelt's, sharing one DuckDB between OrionBelt processes, more CPU than one host has), and how to size them: 2 or more, 2 CPUs or more each, about 150 MB of DuckDB memory per statement a worker runs at once, a worker's statement limit that covers the connections of every source and OrionBelt process using it, and `DB_<NAME>_MAX_CONNECTIONS`, whose default of 10 also limits a source on workers.

## [3.0.0] - 2026-11-11

### Upgrading from 2.36

3.0.0 brings [federated queries](https://ralforion.com/orionbelt-semantic-layer/guide/federation/): a model's data objects can live in different databases, and a query reading several is answered across them. It also changes some answers a 2.36 client gets. Each change is described in full below; these are the ones to check before upgrading.

| What changes | What to do |
|---|---|
| A model named `dimensions`, `measures` or `metrics` is refused at startup, as `model` already was | Rename the model: its OBML `name:`, or its file name |
| A query returns its measures in the order it selects them. Before, measures of independent facts came back grouped by fact, metrics over them after the rest, and measures with a `filterContext` last | A client that reads columns by position, or sorts by position (`field: "3"`), now gets the select's order |
| Window metrics (rank, row number, ntile, lag, lead, first and last value) put NULL last, ranked up or down, on every engine | Ranks of rows with NULL change: ranked down on PostgreSQL, Snowflake and Dremio, ranked up on MySQL, BigQuery and Databricks |
| A Postgres wire or Flight SQL connection to one model reads and lists only that model. A statement naming another loaded model is refused with `MODEL_MISMATCH` | Connect to the model you query (`database=<model>`), or select none (`database=orionbelt`, or Flight SQL without the `database` header) and name the model in `FROM` |
| With `DISABLE_SESSION_LIST=true`, the Postgres wire catalog lists no REST session | Reach a session by its id: `database=<session id>`, or `FROM <session id>` on `database=orionbelt` |
| A model with a `queryTimezone` counts today in that zone, for `current_date()` and every `relative` filter, and labels result timestamps with that zone. A request's `?timezone=` no longer overrides the label | Around midnight, a filter on today returns the model zone's day, not the database's |
| `DELETE /v1/sessions/<model name>` on a model loaded from `MODEL_FILES` returns 403 | Nothing: the model stays loaded |

- **An averaged total, and a metric over a total computed apart, beside a `filterContext` measure.** Both were refused (`INCOMPATIBLE_COMBINATION`): the average total of all orders beside revenue of any region, and a metric such as `{[Median Total]} / {[Revenue]}`, or any metric over a total under `rollup` or `cube`, beside it. The filter context's wrapper keeps the query's own rows in a CTE, and the totals pass now computes what it reads there, unrounded: an average's sum and count, and a metric's other components. Each reads as it does without the `filterContext` measure. `test_total_beside_filter_context_exec.py` compares both on all eight engines. An averaged total beside a measure deduplicated on a repeated object is refused (`GrainDedupUnsupportedError`), with or without a `filterContext`: without one it failed in the database, its sum and count built from values already averaged.
- **Federated queries take `rollup` and `cube` beside a total or a filter context, and at two grains, for measures of independent facts.** Revenue and the number of tickets by region and month, rolled up, beside revenue of any region or a revenue total, or by quarter and month of one date, was refused (`FEDERATION_UNSUPPORTED_QUERY`). Each part now rolls up its fact's dimensions as before, a total and a filter context too, and the union places each part's rows by their `_g_` flags, named per column, so the two grains of one date are rolled up as two columns, as on one database. A total next to the other fact's filter context is computed, under `rollup` too, as on one database; a `grain` beside `rollup` or `cube` gives one database's error (`INCOMPATIBLE_COMBINATION`). `test_federated_shapes_exec.py` runs a total, two filter contexts and two grains under `rollup` on all eight engines.
- **Federated queries take reaggregate metrics beside measures of independent facts.** The average revenue per customer, by region, beside the number of tickets on another data source was refused (`FEDERATION_UNSUPPORTED_QUERY`). The metric is now computed in the part of the fact whose measure it reads, and the union takes it from there, on that fact's groups only, as one database joins the metric's groups to the union's; a count reads 0 on the other groups, in an empty fact and in filled periods, in the type it declares (`'0'` for `dataType: string`), as there. A metric across the facts can read it, and so can `having` and `orderBy`; a reaggregate of a reaggregate works too. Where one database refuses the metric's first stage, because the query groups by or filters on a dimension that fact does not reach (the tickets' severity beside the revenue per customer), the federated query now gives the same error (`UNREACHABLE_REQUIRED_OBJECT`, `UNREACHABLE_FILTER_OBJECT`) rather than leaving the dimension or filter out. Refused still: a reaggregate whose `having` reads the other fact's measure (the revenue per customer of customers with tickets). `test_federated_shapes_exec.py` runs the revenue per customer, and a count of the customers with revenue, beside the tickets on all eight engines.
- **Federated queries take `exists` beside conditions on other sources.** An `exists` or `nonexists` in an `or` with a condition on another data source (the customers with a high ticket, or the orders since March), or in a group true where its subject is missing, was refused (`FEDERATION_UNSUPPORTED_FILTER`): the combine step runs no subquery. On a dimension source, a leg of its own now returns that source's keys the subquery holds for, as a `nonexists` alone already did, and the combine step tests each fact row's key among them: found for `exists`, not for `nonexists`; an order whose customer is missing has none, as one database's `exists` finds no row. Refused still: such an `exists` on the facts' own source, whose fact leg returns groups rather than the rows it tests, one a measure's `filterContext` leaves out, and raw mode. `test_federated_shapes_exec.py` runs an `exists` and a `nonexists` in an `or` on all eight engines.
- **Federated queries take filters on a table column.** A `where` filter, or a measure's `filterContext` include, naming a column (`Customers.Region`) rather than a dimension was refused (`FEDERATION_UNSUPPORTED_FILTER`), even on the facts' own source. One database compares the column as it compares a dimension over it, the same expression in the same time zone; such a filter now runs as one, placed as a dimension's filter is, in a leg or after the join, also in an `or` across sources and beside independent facts. The dimension takes the filter's own name, so a filter context keeping or leaving the filter out by that name, an `exists` on the column, and the errors read it unchanged. Where a dimension, measure, metric or column already has that name (a measure `Orders.Amount`), or another such column has it without its case (`AMOUNT` beside `Amount`), no column becomes a dimension and the query stays refused.
- **Independent facts on several sources take cumulative and window metrics.** Revenue's running total by month beside the CRM's tickets was refused (`FEDERATION_UNSUPPORTED_QUERY`). The combine step now computes running totals, rolling windows, grain-to-date and window metrics (rank, lag, lead, ntile) over the union's periods, at the grain the query selects, as one database computes them over its own. Refused still: a cumulative metric whose date the query filters (one database reads the periods before the filter's first), whose time dimension the query does not select, or over a `windowSpan`; any of them beside a rollup, a cube or one dimension at two grains; reaggregate metrics. `test_federated_shapes_exec.py` runs a running total, a rolling window and a rank on all eight engines.
- **A cube past its engine's grouping-set limit runs as a union of chunks.** Snowflake takes 128 grouping sets in one `GROUP BY` (a cube of 7 dimensions), Postgres and BigQuery 4096 (12): a larger cube failed there. The dialect now sends it as a union of queries, each grouped by `GROUPING SETS` over a chunk of at most that many, and sorts, limits and offsets the union as the query asks, a sort key no column is (an aggregate, a source column) carried as a column of each query. The rows and the `GROUPING()` flags are those of one `CUBE`. A cube whose own columns hold a window function is refused there. `Dialect.max_grouping_sets` holds the limits, probed on all eight engines; `test_cube_chunks_exec.py` runs a cube past them on Snowflake, Postgres and BigQuery, and natively elsewhere, against DuckDB.
- **Independent facts on several sources take rollup, cube, totals, grains, filter contexts, fill, asOf and two grains.** Revenue of the shop's orders beside the CRM's tickets was refused with any of them (`FEDERATION_UNSUPPORTED_QUERY`). The combine step now computes them as one database does. Each fact's part rolls up the dimensions it reaches, and the combine step puts each of its rows in every grouping set of the query it belongs to, then groups by the dimensions and the grouping flags. A total or a value at a coarser grain is spread over every group that shares it, the other fact's groups too. A measure with a filter context is computed in the part of its fact. The combine step fills the periods of the union between the bounds of the query's date filters, and reads a date at each grain the query asks for from its own column. Refused still: a rollup or cube beside a total, grain or filter context, or beside one dimension at two grains; running total, window and reaggregate metrics; a measure reading both facts; coalesce dimensions. A measure of an object both facts join, the number of customers by order month, which one database counts through the orders, is now refused; the parts counted every customer in no month. `test_federated_shapes_exec.py` runs rollup, grain, filter context and fill on all eight engines.
- **Federated queries take a measure of the table the facts are joined to.** Revenue per region and the number of customers per region, with the orders and the customers on two data sources, was refused (`FEDERATION_MULTI_FACT`). One database counts each customer once per region, and also the customers without orders. The customers' leg now returns each customer once, with its key and the columns its measures read, and the combine step counts them the same way: any aggregation of a customer column, with metrics, `having`, sorting, `rollup`, `total` and measure filters. With a filter on the orders, it counts only the customers those orders reach, as one database does, and an `exists` or `nonexists` on the customers' tickets tests the customers without orders too. A customer measure with `allowFanOut: true` counts a customer once per order, from the fact leg's rows. The fact leg returns each customer key, so that leg is not joined as a key map. A customer measure grouped by an order column alone, refused before (`FEDERATION_UNSUPPORTED_JOIN`), runs too. Refused: a customer measure over values its database compares otherwise than DuckDB, such as a distinct count or filter of MySQL text (`FEDERATION_UNSUPPORTED_AGGREGATION`). Refused still (`FEDERATION_MULTI_FACT`): a filter on the orders that a customer without orders passes (`Order Date is_null`), a customer measure with a `filterContext`, a measure of a table the customers are joined to, and sorting by a customer measure the query does not select when it reads no customer dimension. `test_federated_shapes_exec.py` runs it on all eight engines.
- **A federated fact leg joins a small dimension leg as a map of its keys.** A fact leg grouped by a key and something else, revenue by product category and day with the products in a catalog on another source, returned a row per product and day: up to 5,000,000 rows for 10,000 products over 500 days, whatever the number of categories. When the dimension leg is joined on one integer column and returns no more keys than the fact source's key injection limit, the fact leg now runs after it and joins its keys as a map, written into the statement as rows of literals (`VALUES`, on BigQuery an unnested array), each key to the number of its row among the dimension leg's rows, keys of rows holding the same values to one number; it groups by that number instead of the key, and the combine step reads one row per number for that leg, so its query is unchanged. The answer is the same and the leg returns a row per group of what the query reads there. Measured with 5,000,000 groups, mapped to 10, 100 or 1,000: Postgres 16 4.5 s by key against 0.7-1.6 s, MySQL 31 s against 3.5-9.6 s, BigQuery 140 s (fetching the rows) against 1.5-15 s, Databricks 21 s against 1.3-3.6 s, Snowflake 3.6 s against 0.9-1.5 s, Dremio 2.4 s against 0.8-1.0 s; ClickHouse (0.28 s against 0.24-0.32 s) and DuckDB (0.05 s against 0.13 s) group as fast as they join, and the leg still shrinks from 5,000,000 rows of 155 MiB, which spill, to a row per group. A small fact leg can take longer: MySQL 2.1 s by key and 3.4 s mapped for 73,000 groups. Keys of lists and maps count against the key injection limit together, the fewest first; a map takes the place of its key's list, as an inner join where the dimension leg runs a filter, and `0` turns both off. Not mapped: a string key, which the fact source's collation could match to two of the map's keys (`'a'` and `'A'` under MySQL's `utf8mb4_0900_ai_ci`); a key the query also reads as a dimension, a count of distinct values or a `nonexists`; a measure computed from rows; a map making the statement longer than the engine parses; a dimension leg that, with the copy of its rows the map takes, would hold more than `FEDERATION_MAX_LEG_MB` (a spilled leg counts its bytes on disk as held), the copy counted before it is made and the leg's own rows let go before the fact leg runs; on ClickHouse, a key declared (`sqlType`) a 128- or 256-bit integer, which has no common type with the map's `Decimal(38, 0)` keys (they join every integer key up to 64 bits, `UInt64` too, and every decimal). A fact leg reading lists or maps now waits only for the legs it reads them from; the others run beside it. On MySQL a map needs 8.0.19 or later (`VALUES ROW`). A new vendor test runs a mapped fact leg on all eight engines, and the federation planner tests run every plan that may read lists or maps both ways and compare the rows. The guide gains "Key maps" (`docs/guide/federation.md`); `design/PLAN_federation.md` §14 has the measurements.
- **A data source can declare the time zone its sessions run in: `DB_<NAME>_TIMEZONE`.** It falls back to `DB_TIMEZONE`, then to the zone detected from the session. Declare it where none is detected (Databricks, Dremio) or where a source's timestamps without a zone were written in another: results are labeled with it, and a federated query converts from it. A value naming no zone is refused when the source is queried.
- **Federated queries take one-to-one joins.** A one-to-one join between sources, or inside a dimension source, was refused (`FEDERATION_UNSUPPORTED_JOIN`) as if it repeated the rows it joins from, like a many-to-many join; it repeats none. A many-to-many join stays refused: one database repeats a fact row once per match, where a leg returns each value once per key.
- **A federated measure counted once per row of its object can be filtered on the facts.** Computed from the fact leg's rows, a customer measure over their sales (the ages of the customers with a sale of one product) with a filter on a sales column was refused (`FEDERATION_UNSUPPORTED_AGGREGATION`): the combine step reads the customers' rows once each, which hold one row per customer. One database filters the joined rows, then counts each customer once per group; the combine step now does the same, its filter reading the fact rows, the customers' rows holding none of the sales' columns. The filter may read plain columns of the fact's source. Refused still: such a measure reading a sales column as its argument, expression or ordering, a customer column computed from the sales (one database refuses it too), and a dimension read through two such objects, one joined from the other.
- **A federated measure computed from rows can be filtered on a MySQL string.** A measure the combine step computes from the fact leg's rows (a median, a correlation, a measure reading another source, ...) with a filter on a MySQL string was refused (`FEDERATION_UNSUPPORTED_AGGREGATION`): DuckDB compares strings bytewise, where MySQL's collation makes `'Paid'` equal `'paid'`. The fact leg now evaluates such a measure's filters in its own engine and returns the outcome as a column, which the combine step reads; injected keys keep it. The filters may read only plain columns of the fact's source, not computed ones or dates, which the leg returns as stored, and only compare a string with strings (`equals`, `gt`, `inlist`, `between`, ...): the leg evaluates them over groups of values MySQL calls equal, and a pattern (`like`, `ends_with`, ...) tells `'a'` from `'a '`, which `utf8mb4_general_ci` groups, as a comparison with a number tells `'1'` from `'１'`, which `utf8mb4_0900_ai_ci` groups. Refused still: a pattern filter on such a value, or one comparing it with a number, such a value in a filter beside those, as a measure's ordering, expression or argument, and a filter on another source. `test_federated_shapes_exec.py` runs a sum filtered on a mixed-case status, computed from rows, on all eight engines.
- **Federated queries take reaggregate metrics.** A reaggregate metric in a query reading several data sources was refused (`FEDERATION_UNSUPPORTED_METRIC`). The combine step now computes both stages as one database does: the first, the metric's measure grouped by the query's dimensions and its `per` dimensions, is a query of its own over the legs' results, and the second aggregates those values to the query's grain. The legs return the `per` dimensions beside the query's, joined many-to-one from the base object where the query does not join them, and a `per` date as stored, the combine step applying its grain and the query's. With `carryForward`, a filter on the query's dates runs in the combine step, so a member carries its value past it. The metric's `having`, `population: dimension`, a reaggregate metric over another, metrics over it and a query ordering by it alone work too. Refused still (`FEDERATION_UNSUPPORTED_METRIC`): a `per` dimension no many-to-one join reaches from the rows of the metric's measure (the customers' count per order date); one reached by a required join the query does not make in a leg the query or another reaggregate metric reads too, which would drop their rows as well; with `population: dimension`, one whose source's leg reads any other data object, which would list only the members with rows or reached by its rows; and a `per` grain, or a dimension at a grain, over a timestamp with a time zone beside a reaggregate metric per a date. `test_federated_shapes_exec.py` runs reaggregate metrics per a customer and per a date on all eight engines.
- **Federated queries take measures of independent facts on several sources.** Revenue of the shop's orders beside a count of the CRM's tickets, per region, was refused (`FEDERATION_MULTI_FACT`). One database unions such facts, each grouped by the dimensions it reaches under the filters it reaches. Across sources each fact is now a part, a query of its own planned as any query is, and the combine step unions the parts' results and groups them by the dimensions; metrics across the facts, `having`, `orderBy` and `limit` run there. A filter a fact does not reach is left out of its part with the warning one database gives (`FILTER_NOT_APPLIED`, `STATIC_FILTER_NOT_APPLIED`); of an `and` group, only the conditions it does not reach. A fact with no rows the filters keep adds no group, also where it reaches none of the query's dimensions. Refused still (`FEDERATION_UNSUPPORTED_QUERY`): beside such facts, a measure with a total, `grain` or `filterContext`, a `rollup` / `cube`, metrics across periods or reaggregate metrics, `fill`, `asOf`, one dimension at two grains, `dimensionsExclude` and coalesce dimensions. `test_federated_shapes_exec.py` runs independent facts on all eight engines.
- **Federated queries take measures with a grain or a filter context.** A measure with `grain` or `filterContext` in a query reading several data sources was refused (`FEDERATION_UNSUPPORTED_AGGREGATION`). The combine step now computes it as one database does, at its own grain and over its own filters, from the legs' results. A grain adds up groups across the query's other dimensions, as `total: true` does, so an `avg`, a variance or a `count_distinct` with one is computed from rows. A filter that some measure's context leaves out runs after the join, where that measure's scan leaves it out; so does a static filter of the facts' source that a context leaves out (`enforce: always` ones never are). A filter every context keeps still runs in its leg. The fact leg groups by what the moved filters read, so a measure of an object the joins repeat is then computed from rows and counts each of its rows once, with or without a filter context. The legs also return the dimensions an `include` filter reads, checked as a filter's are. Refused: an `exists` that a context leaves out, and an `include` on a `DataObject.Column` rather than a dimension (`FEDERATION_UNSUPPORTED_FILTER`). `test_federated_shapes_exec.py` runs a grain and a filter context on all eight engines.
- **Federated queries run in raw mode.** A raw-mode query (`select.fields`) reading data objects of several data sources was refused (`FEDERATION_UNSUPPORTED_QUERY`). Each leg now returns its rows with the fields read on its source and the join keys, the fact leg each fact row once, and the combine step joins them as one database joins the objects and returns each field under its own name (`Orders.Amount`), distinct, ordered and limited as asked. A filter reading the facts' source alone runs in the fact leg, an `exists` on a subject there too; any other runs after the join, on the columns the legs return, as does a static filter on another source, as beside a measure. The query's `limit` applies after the join, so the fact leg returns every fact row its filters keep, bounded by `FEDERATION_MAX_LEG_ROWS`. Refused still: fields of independent facts, which one database unions (`FEDERATION_UNSUPPORTED_QUERY`), an `exists` on a subject of another source, and, without the model's `queryTimezone`, a filter after the join on a dimension that truncates or casts a timestamp with a time zone, which the combine step would do in its own time zone (`FEDERATION_UNSUPPORTED_FILTER`). `test_federated_shapes_exec.py` runs raw rows filtered across sources and distinct raw rows on seven engines; on BigQuery raw mode fails on one source too, which refuses the dot of `Orders.Order ID` in a column name.
- **Federated queries take `asOf`, `fill`, `usePathNames`, coalesce dimensions, `dimensionsExclude`, and one dimension at two grains.** Each was refused across data sources (`FEDERATION_UNSUPPORTED_QUERY`). A dimension at two grains and `fill` return the dates as stored, as beside a metric across periods, and the combine step applies the grains and fills the periods; a filter on `fill`'s time dimension runs there too, so the periods span its bounds as on one database. `asOf` evaluates a cumulative metric over those dates. A `usePathNames` path between two sources is the edge the combine step joins, and one within a source is that source's leg's own join: an order's support employee beside the orders on the shop is read by the support key there. Coalesce dimensions return each member from its leg, coalesced in the combine step. `dimensionsExclude` over one group of dimensions answers as on one database.
- **The federated query shapes added since 2.36.0 run on all eight engines.** `test_federated_shapes_exec.py` runs every leg of an `exists` and a `nonexists` subquery, a chain of three sources, a role-playing dimension, a filter after the join on the day of a month the query selects, a running total, a rolling window, a rank, and a running total and month-over-month change shown from February, on DuckDB, PostgreSQL, MySQL, ClickHouse, Snowflake, BigQuery, Databricks and Dremio, every source the engine itself: the combined answer is the engine's own over one source on all eight.
- **Federated queries compute cumulative, period-over-period and window metrics.** A query across data sources with a cumulative (running total, rolling window, grain-to-date, rolling time span), period-over-period or window metric was refused (`FEDERATION_UNSUPPORTED_METRIC`). The combine step now computes it over the combined values, as one database computes it over its own. The legs return each date column as stored, an order at its own date, and the combine step applies the grains, the dimension's declared one and the query's, so a rolling window over months counts months and a time span reads each order's date; every dimension over one date column reads that one column there. A filter on the metric's time dimension, or on another dimension over its date column, runs in the combine step too: it says which periods to show, not which the metric reads, so shown from February, February's change is against January and March's running total counts January, as on one database. Its static filters run in its own leg, and the `enforce: always` ones in the subquery too, as on one database; on the measures' source, the fact leg read again with injected keys does the same.

The far source is now a dimension leg of its own: the middle source's leg returns the key into it beside its own, and the combine step joins the far leg from the middle one, as one database joins the regions from the customers. A chain coming back to the measures' source (regions on the shop, reached through the CRM) is a leg of its own there. The filter now runs on the data source of its subject, with its whole subquery: in the fact leg, or in a dimension leg for `exists` (whose keys the fact leg then reads). A `nonexists` on a dimension source holds for a fact row with no row there, so a leg of its own returns the keys the subquery holds for and the combine step keeps the fact rows whose key is not among them, as one database keeps an order whose customer is missing. Refused, as `FEDERATION_UNSUPPORTED_FILTER`: a subquery reading another source than its subject, and an `exists` that would run after the join.

Value search (`POST .../values`) over a dimension with a filter on another source, refused the same way, runs too: it now sends a federated plan to the federated executor, as `query/execute` does.

Refused still: a measure reading a column computed from columns of two sources, and one counted once per row of another object of the fact's source that reads another source (`FEDERATION_MEASURE_ACROSS_SOURCES`).

How a query across data sources is split into legs and a DuckDB combine query, with the SQL OBSL emits for an example (MySQL orders, PostgreSQL customers); where each filter runs and when the fact leg reads only the injected keys; how each aggregation combines, from partial results or from the fact leg's rows, and how an object the joins repeat is counted once; the values engines compare otherwise; the run time settings; and every limitation, grouped by query shape, joins, measures, filters, run time, whole-model operations and the results that can differ from one database. The federation section of the Data Sources guide now points there.
- **A measure of an object the joins repeat counts each of its rows once across data sources, whatever the query groups by.** Federation P5's combine-side dedup (`design/PLAN_federation.md` §5.5): a `sum`, `count`, `avg` or variance of customers' ages over their sales was refused (`FEDERATION_UNSUPPORTED_AGGREGATION`) when the fact leg grouped by more than one value per customer, a key to another source on the sales side, a filter after the join, or a subtotal or total adding groups across one: partial results counted a customer once per product (ages 10 and 20 summed to 40 for 30). So was a `count_distinct` beside measures of another data object. Such a query is now computed from the fact leg's rows, which also carry the identity of each object measures read through the sales (its `primaryKey`, else the key its join reaches it by) and a count over its rows. The combine query reads each such object's rows once each, with what its measures read and the dimensions and keys the query reads of it, and its own deduplication counts each once per group, as one database does. The count makes the leg return the customers without a sale too, and every measure of the customers reads them, a `count_distinct` or a `max` as much as a `sum`: one database puts them in the group of their own region, and so does the combine step. That also corrects a query computed from rows since #695 for some other reason: a `max` of a customer column left those customers out. Refused: such a measure reading a value of which one customer has several (a column of the sales), and a dimension read through two such objects. Compared with one source on DuckDB under groups, filters, subtotals, totals, an expression, a measure filter on the customer's region, a metric, two such objects, and `min`, `max`, `first`, `last` and `count_distinct` beside a sum, and with exact arithmetic on all eight engines.
- **A median, a percentile, a correlation and every other measure that does not combine from partial results work across data sources.** Federation P5's raw-row legs (`design/PLAN_federation.md` §5.3): `median`, `percentile_cont`, `percentile_disc`, `mode`, `first`, `last`, `listagg`, `corr`, the covariances and regressions, a variance or standard deviation of floats or of a decimal its leg does not square exactly, `distinct` aggregations, a `count_distinct` of an expression or under measure filters, and an `avg`, `count_distinct` or variance with `total: true` were refused across data sources (`FEDERATION_UNSUPPORTED_AGGREGATION`). When a query has one, the fact leg now also groups by every column the measures read and counts each group's rows, and the combine query repeats each group that many times, a `range()` join in its own SQL, and computes every measure of the query from those rows as one database does. A leg's rows count against `FEDERATION_MAX_LEG_ROWS` by the rows they stand for: 7 orders returned as 5 groups are 7 (`FEDERATION_LEG_TOO_LARGE`). Over doubles far from zero the result depends on the order values are added in, as on one source. Still refused: in such a query, a measure of an object the joins repeat that one database counts once per row, and a measure comparing values its engine compares otherwise than DuckDB (a MySQL string, a ClickHouse float it counts). Compared with one source on DuckDB, and with exact arithmetic for the fact leg on all eight engines (`test_federated_rows_exec.py`).
- **A federated fact leg reads only the keys a filtered dimension leg returns.** Federation P5's key injection (`design/PLAN_federation.md` §4.3): a filter on another source's dimensions runs in that source's leg, but the fact leg still aggregated every key. When the dimension leg is joined on one integer or string column, the fact leg now runs after it and reads `key IN (...)` of the keys it returned, up to the fact source's limit over all such legs, the fewest first; no key at all reads no fact row (`LIMIT 0`). The answer is unchanged; only the fact rows the combine step would drop are not read. Measured with 5 million orders over 1 million customers, the fact leg went from 1.3 s to 0.10-0.14 s on Postgres 16 (10 to 10,000 keys), from 7 s to 0.02-0.12 s on MySQL with an index, from 0.85 s to 0.02-0.08 s on ClickHouse; through the REST executor on Postgres 16, 1.9 s became 0.11 s. Limits: 10,000 keys on Postgres, MySQL and ClickHouse (past it MySQL stops using an index and ClickHouse refuses the statement) and on BigQuery (every key 21 s, most of it fetching a million rows, against 2.2 s for 10,000 keys), 1,000 on DuckDB, and on Snowflake, Databricks and Dremio, which return every key in 0.4-2.1 s (Snowflake took 1.4 s for a new list of 10,000); `DB_<NAME>_KEY_INJECTION_MAX_KEYS` sets it per source, `DB_KEY_INJECTION_MAX_KEYS` for all, `0` turns it off (as Postgres 13 and older need: they test an `IN` list one value at a time). A list making a ClickHouse statement longer than its default `max_query_size`, or a BigQuery one longer than its 1,024K characters, is not read, nor a string key holding a NUL (Postgres ends the statement's text at it). A new vendor test runs an injected fact leg with integer keys and with string keys holding a quote, a backslash and text outside Latin-1 on all eight engines.
- **A variance or standard deviation combines across data sources.** Federation P5's third item (`design/PLAN_federation.md` §5.2): `variance`, `var_pop`, `stddev` and `stddev_pop` were refused across data sources (`FEDERATION_UNSUPPORTED_AGGREGATION`). Per-group statistics do not combine, but their moments do: the fact leg now returns each group's count, sum and sum of squares, each value squared in the widest exact type its engine has (`Dialect.exact_square`), and the combine query computes the statistic from their totals as 128-bit integers, shifted by the integer mean so no term overflows, rounding once, to a double. Probed on all eight engines, moments summed as doubles were wrong by up to 4e19 relative far from zero; the exact moments match the exact statistic to a double's precision on every engine, Snowflake and Dremio included, whose own `STDDEV` cancels there. The values must be integers or a decimal column declared with `sqlPrecision` and `sqlScale`, of up to 3 places on Databricks and Dremio (a wider product rounds to 6 places there, and on Dremio a value past a narrower type casts to 0), 6 on Snowflake and 15 on MySQL. Floats, `total: true`, covariance, correlation and regression are refused by name, and a sum of squares past 128 bits raises rather than wrapping.
- **A count of distinct values combines across data sources.** Federation P5's second item (`design/PLAN_federation.md` §5.2): a query across data sources refused `count_distinct` (`FEDERATION_UNSUPPORTED_AGGREGATION`). Counts of distinct values do not add up, so the fact leg now also groups by the column the measure counts, and the combine query counts that column's distinct values across every group they reach; a `count` with `distinct: true` combines the same way. The query's other measures must read the counted column's data object, whose sums, counts and averages still combine exactly at that finer grain; beside a measure of another object the count is refused, since a one-side measure would repeat per counted value and the rows kept for one object are not the other's. The leg's extra rows are bounded by `FEDERATION_MAX_LEG_ROWS`. Probed on all eight engines: the combined count equals each engine's own `COUNT(DISTINCT)`, except where the engine's equality is not DuckDB's: a MySQL string column under its default case- and accent-insensitive collation (`'a'` and `'A'` are one value there, two in the combine step), as for any string compared across sources, and ClickHouse floats (`0.0` and `-0.0` are two values there, one in DuckDB); both are documented. A `count_distinct` of an expression, of several columns or under measure filters, one with `total: true`, and other `distinct` aggregations are still refused by name.
- **An average combines across data sources.** Federation P5's first item (`design/PLAN_federation.md` §5.1): a query across data sources could not use an `avg` measure (`FEDERATION_UNSUPPORTED_AGGREGATION`). The fact leg now returns the average's sum and count under the measure's filters, and the combine query divides the summed sums by the summed counts, so the result is the average of the rows rather than of per-group averages. An integer or decimal measure is divided exactly in integer arithmetic and rounded half away from zero to the measure's type, as PostgreSQL, MySQL and Snowflake round their own `AVG`; DuckDB's division would be floating point, which drifted at sixteen digits and failed to cast a `DECIMAL(18, 2)` average near its width back to that type. A `float` measure divides as doubles. Decimal sums are read at 9 places, BigQuery's `NUMERIC` scale and the most any engine returned; a sum with more, or a floating-point sum for a decimal measure, is refused (`FEDERATION_LEG_TYPE`), never rounded. HAVING, ORDER BY and derived metrics read the average unrounded, at 18 places or more, as they read a raw `AVG` in one database, and the measure's column rounds it once; the integer part is divided before the fraction is scaled, so a `decimal(38, 18)` average of values near 10^16 does not overflow 128 bits. The partial columns get names no declared measure has. Probed on all eight engines with integers past 2**53, a tie past a double's mantissa, negatives, an empty group and a decimal at its declared width: exact on every one. An `avg` with `total: true` is still refused.
- **Queries across data sources run on every surface.** Federation P4 (`design/PLAN_federation.md`): OBSQL over REST (`query/semantic-ql`), Flight SQL and pgwire, and `obsl execute`, run a federated query as `query/execute` does, each leg on its own data source and the combine in DuckDB, within the same admission, connection and spill bounds. REST, Flight SQL and pgwire share the result cache, legs included, so a query one of them cached is a hit on the others; Flight streams the schema it advertised. A query on a model read from several sources that reads only one of them now runs on that source on these surfaces too, and in value search; before, each refused the whole model with `FEDERATION_NOT_ENABLED`. Lineage names the data source each table is read from (`data_source` on a data object node, `source: <name>` in Mermaid, `obsl:dataSource` in Turtle). The one-shot batch runs it too, through the same cache, and lists the legs in `federation`, compiled only or executed; the database `EXPLAIN` of `query/plan` explains each leg on its own data source (`database_explain_legs`, with `leg` and `data_source`), a leg that fails as a warning naming it. A one-source query on such a model is executed, cached and explained in the dialect it was compiled for, on these two as on the others.
- **Large legs of a federated query spill to disk.** Federation P3's last item (`design/PLAN_federation.md` §7.2), off unless `FEDERATION_SPILL_DIR` names a directory on real disk. A leg is then read batch by batch and held in memory up to `FEDERATION_SPILL_THRESHOLD_MB` (default 64); past that it is written to a file in the Arrow IPC stream format, which the DuckDB combine step reads memory-mapped, so the operating system can page it out, and DuckDB spills its own join and sort state into the same place. Each query writes into a directory of its own, mode 0700, removed when the query ends, also on failure. One query may spill `FEDERATION_SPILL_MAX_MB` (default 4096, else `FEDERATION_SPILL_TOO_LARGE`), the queries running at once `FEDERATION_SPILL_BUDGET_MB` together (default 16384, else `FEDERATION_SPILL_FULL`, 503). A spilled leg is not stored in the result cache, which would read it back into memory; the combined result still is. Every driver streams a leg. DuckDB, and the Postgres, Snowflake and Databricks cursors, read a result page by page through `fetch_record_batch()` (new in `ob-postgres`, `ob-snowflake` and `ob-databricks`). `ob-mysql` (over ADBC), `ob-clickhouse`, `ob-bigquery` and `ob-dremio` read a whole result in `execute()`, as PEP 249 callers expect, so they gain `execute_stream()`, which streams it instead and is what a spilling leg uses. Each holds every page to the first page's types: Snowflake and BigQuery pick a page's integer width from its values, and a page that does not fit fails the read rather than changing a value. `ob-databricks` now declares its `pyarrow` dependency, optional in the connector since 4.0 and needed for its Arrow results. DuckDB's own spill in the combine step is capped at `FEDERATION_SPILL_MAX_MB` per query, so the most the directory holds is `FEDERATION_SPILL_BUDGET_MB + FEDERATION_MAX_CONCURRENT x FEDERATION_SPILL_MAX_MB`. A disk that fills, or a directory that cannot be written, is a 503 naming `FEDERATION_SPILL_DIR`, not a database failure. The API and Flight images create `/app/spill` owned by their `app` user, so a named volume mounted there is writable; the Docker guide shows the volume, its size, and the same for Kubernetes. DuckDB is now required at 1.5.6 or later (was 1.4, in `ob-duckdb` too): a DuckDB leg streams through `to_arrow_reader()`, which 1.4 lacks, so on 1.4 a leg was fetched whole and never spilled.
- **A data source's connections are bounded.** A query used to open a new connection whenever its source had none idle, so N concurrent queries meant N connections, enough to exhaust a database's connection limit. Each source now allows `DB_<NAME>_MAX_CONNECTIONS` (then `DB_MAX_CONNECTIONS`, default 10, `0` for no limit) connections in use at once, counted across REST, pgwire, Flight SQL and federated legs, pooled or opened for one query. A query past the bound waits its turn in order of arrival, so new queries cannot starve an earlier one, for up to `DB_<NAME>_ACQUIRE_TIMEOUT_SECONDS` (then `DB_ACQUIRE_TIMEOUT_SECONDS`, default 30); a query still waiting is refused with `DATA_SOURCE_BUSY` (HTTP 503), naming the source and the setting to raise. Idle connections kept for reuse never exceed the bound.
- **Queries across data sources run through the REST API.** Federation P3 (`design/PLAN_federation.md`): `query/execute` runs a federated query's legs at once, each on its own data source, and combines them in an in-memory DuckDB. The result is cached like any query's, keyed by the combine query and every leg's SQL with its data source, with the shortest TTL of the tables the legs read, and never outliving a cached leg it was computed from; a hit runs nothing. Each leg is also cached on its own, so a query that changes only the combine step (a filter on another source, HAVING, ORDER BY, LIMIT) reuses the cached legs. Leg results are made exact before combining: Postgres `numeric`, which arrives as text, becomes a decimal at the scale its values carry, and a decimal past 38 digits narrows when its values fit; a value no decimal holds is refused (`FEDERATION_LEG_TYPE`). A failing leg names its data source. Bounds per process: `FEDERATION_MAX_CONCURRENT` queries at once, the others waiting in order of arrival up to `FEDERATION_QUEUE_TIMEOUT_SECONDS`, then 503 `FEDERATION_BUSY`; legs on a pool of `FEDERATION_LEG_THREADS`; at most `FEDERATION_MAX_LEG_ROWS` rows per leg (`FEDERATION_LEG_TOO_LARGE`); each combine step limited to `FEDERATION_COMBINE_THREADS` threads and `FEDERATION_COMBINE_MEMORY_LIMIT`. The execute response lists the legs in `federation`. A query on a model read from several sources that reads only one of them runs on that source, in its dialect.
- **Queries across data sources compile into one query per source and a DuckDB query combining them.** Federation P2 (`design/PLAN_federation.md`), compile only: executing such a query is still refused with `FEDERATION_NOT_ENABLED`. A query reading data objects of several sources is split into islands of joined objects on one source. The fact island, holding the measures, becomes a leg grouped by its dimensions and the join keys that pre-aggregates the measures; every other island, joined to it many-to-one, a leg returning its keys with the dimensions read there. Each leg is compiled by the existing pipeline in its source's dialect, so it keeps every rule of a single-source query. The combine query is the original query compiled for DuckDB over the legs: it joins them on the keys, re-aggregates (`SUM` of sums and counts, `MIN` / `MAX`), evaluates derived metrics and runs HAVING, ORDER BY and LIMIT. A filter on the fact island runs in its leg, any other in the combine query after the join, and so does a static model filter on another island, on a column its leg returns, so a tenant filter cannot fail open and a filter true for NULL keeps unmatched rows. Partial sums stay in the engine's own type, neither rounded nor bounded, until combined; the measure's type and `defaultValue` apply to the combined value, and a count over no rows is 0, as a SQL `COUNT` is. What does not split exactly is refused by name (`FEDERATION_MULTI_FACT`, `FEDERATION_UNSUPPORTED_AGGREGATION` for `avg` and `count_distinct` among others, `FEDERATION_MEASURE_ACROSS_SOURCES`, `FEDERATION_UNSUPPORTED_METRIC`, `FEDERATION_UNSUPPORTED_JOIN`, `FEDERATION_UNSUPPORTED_FILTER`). `query/sql`, `semantic-ql/compile` and `obsl compile` show the legs (`federation` in the response). A differential test runs the plan over two DuckDB files and compares it with the same query on one file.
- **A data object names its own data source: `dataSource`.** The first step of federation (`design/PLAN_federation.md`, P1): a data object can say which configured data source its table is read from, overriding `settings.defaultDataSource`. A model whose objects all name one source runs on it. A query on a model whose objects are read from more than one source is refused with `FEDERATION_NOT_ENABLED`, naming which objects read from which source; the model still loads, so it can be prepared ahead of federation. An object read through `nestedIn` takes its parent's source. Where queries execute, an unknown name fails the load at `dataObjects.<name>.dataSource`. In the JSON schema, the schema API (`data_source`), model inheritance, the OBSL graph (`obsl:dataSource`, with a SHACL shape) and the OSI converter (`obml_data_source`, ships in osi-orionbelt 0.6.1).
- **Named data sources: a model picks the database its queries run on.** One process could connect to one database per dialect, so two Postgres databases needed two deployments. Data sources are now declared by name in the environment (`OBSL_DATABASES=shop-eu,shop-us`, each with `DB_<NAME>_TYPE` and the dialect's usual variables behind a `DB_<NAME>_` prefix, falling back to the unprefixed ones), and a model names its own in the new OBML setting `settings.defaultDataSource`: a name only, never credentials, so one model file runs unchanged against a test and a production database. A model that names none runs on the sole data source of its dialect, and a query is refused, naming the candidates, when there are several. REST, Flight SQL, pgwire, the one-shot batch, value search, the plan endpoint's database EXPLAIN, the datasource probe and the CLI all send a model to the same source, and the result cache is scoped to it. A Flight query runs on the source it was planned with, cached or not, since the call fetching the ticket need not name the model again. New `GET /v1/datasources` and `obsl datasources` list the configured sources with their name, dialect, description and database, never a host, user, password or token. Model load (`POST /v1/sessions/{id}/models`) takes `datasource` to run the model on another source, and `obsl execute` takes `--datasource`; the same YAML on another source is another model, with its own id and cache entries. Where queries execute, a model naming a source that is not configured, or one of another dialect, fails to load (`DATA_SOURCE_UNAVAILABLE`), at startup for `MODEL_FILES`. Without `OBSL_DATABASES` nothing changes, cache keys included. In the JSON schema, the schema API's `model_settings` and the OSI converter (through the settings round-trip; the vendored schema ships in osi-orionbelt 0.6.1); and in the OBSL graph as `obsl:defaultDataSource` on the model, with a SHACL shape, apart from each object's own `obsl:dataSource`, so a SPARQL query reads every object's source as `COALESCE(?declared, ?default)`, a nested object's from the top of its `nestedIn` chain (the OBSL guide gives the query). It is the first model setting in the ontology.
- **OrionBelt Analytics' connection variable names are accepted.** `POSTGRES_DATABASE`, `POSTGRES_USERNAME`, `MYSQL_USERNAME`, `SNOWFLAKE_USERNAME`, `BIGQUERY_PROJECT_ID`, `BIGQUERY_CREDENTIALS_PATH` and `DUCKDB_DATABASE_PATH` stand in for OBSL's names when those are unset, so an `.env` written for Analytics connects here too. The canonical name wins when both are set. Groundwork for named data sources (`OBSL_DATABASES`, `design/PLAN_named_connections.md`): connection pools are now kept per data source rather than per dialect, which changes nothing while each dialect has one.

### Changed

- **`dimensions`, `measures` and `metrics` are reserved model names.** Every model's catalog schema holds tables of these names beside `model`, on the Postgres wire and on Flight SQL, so a model named `measures` read as that table: `DESCRIBE measures.model` was taken for the connected model's `measures` view. Such a name is now refused at startup, like `model`.
- **Window metrics order a NULL last, on every engine.** A rank, row number, ntile, lag, lead or first and last value left the place of a NULL in its window to the engine: ranked down by revenue, a region without revenue ranked first on PostgreSQL, Snowflake and Dremio and last elsewhere; ranked up, first on MySQL, BigQuery and Databricks; and there a row without a date was the period before January, whose prior revenue it gave. A federated query, ranking in DuckDB, put it last. Each window metric now orders a NULL last, up or down, as a running total and a framed window already did, so one database answers the same on all eight engines and a federated query as one database does. `test_window_null_order_exec.py` runs a rank down, a rank up and a lag on all eight.
- **Federated queries sort text as its database does.** The combine step sorts in DuckDB, which orders text by its bytes, `'C'` before `'b'`, where PostgreSQL's `en_US.utf8` and MySQL's `utf8mb4_0900_ai_ci` put `'b'` first: revenue by sales rep listed `Ann`, `Cid`, `bob` where one database lists `Ann`, `bob`, `Cid`, and a limited query kept other rows. A sort by a text dimension or raw-mode field is now ranked by the leg returning it, `DENSE_RANK() OVER (ORDER BY ...)` in its own engine, and the combine step sorts and limits by that rank, also for a limited query naming no sort and under `rollup` or `cube`. Still sorted by bytes: measures of independent facts on several databases (each fact's part would rank only the values it reaches), a coalesce dimension, a sort by column position, and a sort that also names a measure the query does not select. `test_federated_shapes_exec.py` and `test_federated_equality_exec.py` compare the sorted rows with the engine's own on all eight engines.
- **Federated queries sort NULL where the facts' database does.** One database leaves the place of NULL in a sort to its engine: PostgreSQL, Snowflake and Dremio put it last when sorting ascending and first when sorting descending, MySQL, BigQuery and Databricks the other way round, DuckDB and ClickHouse last either way. A federated query sorts in DuckDB, which put it last: revenue by region sorted down on PostgreSQL showed the group without a region last, not first, and a query with `limit` and no `orderBy`, sorted by its dimensions, kept other rows on MySQL. A sort without `nulls` now places NULL as the facts' database does, also in that limited query (by its fields in raw mode). Measures of independent facts on databases that place NULL differently keep DuckDB's place, as `rollup` and `cube` keep NULL first. `test_federated_shapes_exec.py` compares the sorted rows with the engine's own on all eight engines.
- **The federation limitations are rewritten in plain language.** The Limitations section of the federation guide now starts with a table: find what your query does, see when it is refused, and jump to the section. Each row gives an example from the shop and CRM model, what to do instead, and the error. Three rows are new: `exists` on a list in another database, such as a customer's tags (filter on the tag dimension instead, `Tag = 'vip'`, which returns the same orders), a timestamp with a time zone grouped by period with `fill` or at two grains, and where NULLs are sorted (set `nulls: first` or `nulls: last`). Each result that can differ from one database now says what to do about it.
- **Every federation refusal has a hint.** Eight refusals had none. Each now says what to do instead, and `FEDERATION_MULTI_FACT` says to query each data source's measures separately.
- **A federated leg refused for its size says why.** `FEDERATION_LEG_TOO_LARGE` said only that a leg returned too many rows, and to filter or select fewer dimensions. A leg returns a row per key of each join between sources it holds, beside the query's dimensions, so revenue by region with the customers on another source sums per customer, whatever the number of regions. The refusal now names those joins (`Orders.Order Customer -> Customers.Customer ID (between 'shop' and 'crm')`), and suggests a filter, a join on a column with fewer values, or larger legs with spill. A leg returning rows, of a query of fields or of a measure computed from rows, is explained by them instead: only a filter narrows it. The federation guide gains "Where to join the sources": put a join between sources on a dimension with few values both share (a region, a category, a legal entity), not on a key of single records.
- **A federated leg may return 5,000,000 rows by default** (`FEDERATION_MAX_LEG_ROWS`, was 1,000,000). Measured, revenue by region over 5,000,000 customers, a fact leg from PostgreSQL and a dimension leg of 5,000,000 rows each, took 730 MB and 6 s, and four such queries at once, the default `FEDERATION_MAX_CONCURRENT`, 2.7 GB: about 75 MB per million narrow leg rows. A server with less memory lowers the limit or the concurrency, or spills (`FEDERATION_SPILL_DIR`).
- **Federated legs spill to disk by default.** Spilling was off unless `FEDERATION_SPILL_DIR` named a directory. Unset, a leg past `FEDERATION_SPILL_THRESHOLD_MB` (64) now goes to the system's temp directory, unless that is in memory: on a tmpfs or ramfs, and on Cloud Run, whose filesystem is in memory, nothing spills, as before. `FEDERATION_SPILL_DIR=off` turns it off. Spilling trades time for memory, for legs past the threshold only: measured with legs of 11,000,000 rows, one query took 5.6 s instead of 5.0 and four at once a median of 9.5 s instead of 6.0, holding 375 MB of memory the operating system cannot reclaim instead of 665, and 639 MB instead of 1,915. In the Docker images the temp directory is the container's writable layer; a volume at `/app/spill` remains the better place.
- **A federated leg is bounded by its memory too: `FEDERATION_MAX_LEG_MB` (default 512).** Rows alone do not say what a leg takes: 5,000,000 rows of a key and two partial results take 154 MB, and each text field adds its length plus 4 bytes a row. Every leg now streams batch by batch, spilling or not, and a leg held in memory is refused with `FEDERATION_LEG_TOO_LARGE` as soon as it takes more, before it is whole. A leg served from the cache is held to it too. A spilled leg is bounded by the spill limits instead, except for the columns the combine step needs converted (a PostgreSQL `numeric` arrives as text and becomes a decimal), which it holds in memory within the limit. `FEDERATION_MAX_LEG_ROWS` stays as the backstop.
- **A filter on another data source runs in that source's leg.** A federated query ran every filter on another source's dimensions in the combine step, after that source's leg had returned all of its keys. A filter on one source's dimensions that is never true where they are all NULL (`=`, `!=`, `in`, comparisons, `like`, `relative` and the others, but not `is_null` or `blank`, and groups of them by SQL's three-valued logic) now runs in that source's leg, and the combine step keeps the fact rows the leg matched, as the filter on a left-joined object does in one database. The leg returns only the rows the filter keeps (with a DuckDB fact leg over 5 million orders, 0.16 s became 0.04 s), compared as its own engine compares them: a MySQL string filter follows the column's collation, as in one database, where DuckDB compared bytes. A relative date filter on another source is no longer refused. A filter reading more than one source, or true for NULL, still runs in the combine step. Changing such a filter reruns that source's leg only; the fact leg is served from the cache.
- **DuckDB results go straight to Arrow.** A query on DuckDB was executed, held as rows and then copied into an Arrow table, which DuckDB 2.0 warns about on every query ("Arrow output on a DB-API result makes an extra copy of the rows"). REST, pgwire and the UI now read the result as a relation that builds the table directly. An error raised while the result is read surfaces once, without running the query a second time. The session timezone probe runs on its own cursor, as DuckDB 2.0 refuses a query on a connection whose previous result was not read to the end. Flight SQL reads through the `ob-duckdb` cursor, which keeps the copy: a PEP 249 cursor runs its query in `execute()`, and DuckDB has no copy-free Arrow read of an executed result.

### Fixed

- **MySQL: a query on today is never served from the result cache.** A `relative` filter renders `CURDATE()`, which the cache's check for clock reads did not know, so "the last 7 days" was cached for its TTL wherever the cache held the query, and could answer with yesterday's window after midnight. `CURDATE`, `CURTIME`, `UTC_DATE`, `UTC_TIME` and `UTC_TIMESTAMP` (today in a model's `queryTimezone` on MySQL) now count as clock reads. A test compiles a relative filter and `current_date()` on all eight dialects, with and without `queryTimezone`, and asserts the cache skips each.
- **Today is counted in the model's `queryTimezone`.** `queryTimezone` read a model's timestamp columns in its zone, but today's date, for `current_date()` and every `relative` filter, stayed the database session's, so a filter on today compared dates of two zones. On BigQuery, whose `CURRENT_DATE` is UTC's by default, a model in New York filtered to today returned no rows from 19:00 New York time (20:00 in summer); a model east of UTC, in Europe/Zagreb, returned the day before until UTC's midnight. Today is now the current moment read in the query zone, as a column is: `CURRENT_DATE('America/New_York')` on BigQuery, `CAST(CURRENT_TIMESTAMP AT TIME ZONE 'America/New_York' AS DATE)` on DuckDB and Postgres, `CONVERT_TIMEZONE` on Snowflake and Dremio, `toTimeZone(now(), ...)` on ClickHouse, `convert_timezone` on Databricks and `CONVERT_TZ(UTC_TIMESTAMP(), ...)` on MySQL; in a federated query, on each leg and in the combine step. Probed on all eight engines with the session 25 hours from the model's zone. Without `queryTimezone`, today is the session's, as before.
- **Dremio: a rollup or cube filtered with `=` on a dimension keeps its subtotal rows NULL there.** Under `where Region = EU`, Dremio's planner carried the filter's constant into the rolled-up rows another query read, so the grand total showed `Region = EU` with `_g_Region = 1`, and a `filterContext` measure joined on it read NULL (revenue of any region, 238.00 on the grand total, came back empty). It took no more than reading the rollup from a CTE: a total, a `filterContext` measure, or the measures of two facts did. Each rolled-up dimension is now returned as `CASE WHEN GROUPING(x) = 0 THEN x END` on Dremio, which its planner does not replace, and a key named like its column is qualified, since Dremio reads that name in the `GROUP BY` as the alias. `test_rollup_filter_context_exec.py` adds the `=` filter, and `test_federated_shapes_exec.py` a rollup of two facts in one region, on all eight engines.
- **A rollup or cube of a coalesced dimension runs.** Beside two facts, `{coalesce: [Sales Region, Purchase Region], as: Region}` is grouped by the `COALESCE` of its members, and its `GROUPING()` flag read the alias `Region`, which PostgreSQL, DuckDB, MySQL, ClickHouse, BigQuery and Databricks refuse; Dremio refused it once it returned each key through its flag. The flag now reads the `COALESCE` key. `test_rollup_coalesced_exec.py` runs it, rolled up and as a cube, on all eight engines.
- **A coalesced dimension is sorted by its alias when a query has a `limit`, `rollup` or `cube`.** Such a query without an `orderBy` is sorted by its dimensions. Beside two facts, a coalesced dimension (`{coalesce: [Sales Region, Purchase Region], as: Region}`) was sorted by its members, which the query neither returns nor groups by, so the database refused it: `limit: 2` alone failed. It is now sorted by its alias, as `orderBy: Region` sorts it. A query that returns the members as columns, as one on one fact does, is still sorted by them. `test_rollup_coalesced_exec.py` checks the order on all eight engines.
- **A coalesced dimension works beside totals, grain overrides and window metrics.** Over two facts, a coalesce group is one column, its alias (`Region` for `{coalesce: [Sales Region, Purchase Region], as: Region}`). Beside a `total: true` measure, a metric over one, a grain override or a window metric, the query named the group's members instead, which it does not return, and every engine refused it. These read the alias now, under `rollup` and `cube` too. A running total, or a window metric ordered by a date the query coalesces, is refused there (`INCOMPATIBLE_COMBINATION`) rather than compiled to SQL naming the members. `test_rollup_coalesced_exec.py` runs a total and a metric over it beside the coalesced region on all eight engines.
- **A Postgres wire statement may start with a comment.** A client may tag a statement, as DBeaver prefixes `/* ApplicationName=... */`. The router recognised the statements it answers itself (`SELECT 1`, `SELECT version()`, `SELECT current_schema()`, `SHOW`, a SELECT of constants) by their first word, so a tagged one went to the semantic translator and was refused (`UNSUPPORTED_SQL_FEATURE`). Comments before a statement's first token are now dropped before it is routed, over the simple and the extended protocol; comments after it stay.
- **The Postgres wire catalog reads quoted and `orionbelt`-qualified system relations.** `SELECT nspname FROM "pg_catalog"."pg_namespace"` failed with `Table with name _obsl_pg_namespace does not exist`, and so did `pg_catalog."pg_class"` and the other relations OBSL shadows (`pg_class`, `pg_attribute`, `pg_type`, `pg_database`, `pg_settings`, `pg_index`, ...). A name qualified by the brand database (`orionbelt.pg_catalog.pg_class`, `orionbelt.information_schema.tables`) failed for every relation, and `"information_schema"."schemata"` with a parser error. Postgres reads each as the unquoted, unqualified name, and now so does the catalog. Only names in the SQL itself are read this way: string literals in every form (`'...'`, `E'...'`, `$$...$$`, `$é$...$é$`), comments and other quoted names keep their text. Splitting a message into statements reads quotes the same way: a dollar quote tagged with a non-ASCII letter, a `$` inside a name (`a$b$c`) and an `e` ending a word before a literal (`name'a\'`) no longer split a statement in two or join two into one.

A static filter it cannot reach was reported for no measure: an `enforce: always` filter refused the query with "the fact behind  cannot reach 'Tickets'", and a relevant one warned that "this query" could not reach it, though the query did. - **A Flight SQL connection reads only the model it selects.** On a connection whose `database` header selects one model (`commerce`), a statement naming another loaded model by its schema answered for the connected model: `SELECT ... FROM shop.measures` returned commerce's rows, and `SELECT * FROM shop._measures_metadata`, `DESCRIBE shop` and `SHOW COLUMNS FROM shop` listed commerce's measures and columns as the shop's. Every object a subquery reads now counts: its join path, the objects its filters and the `enforce: always` static filters read, and the objects joined to reach them. The query is planned across the sources (refused as above for now).
- **Online validation checks a model read from several data sources.** `obsl validate --online` and `POST .../validate?online=true` probed one data source per model, so on a model whose data objects name several (a federated model) the check did not run: validation reported `DATASOURCE_UNAVAILABLE` with `FEDERATION_NOT_ENABLED` and the model as invalid. Each data object is now probed on its own source, in that source's dialect, as its queries read it. A source that cannot be reached (not configured, ambiguous, of another dialect than one given explicitly) is reported at the `dataSource` that names it, and the other sources are probed all the same.
- **`mode` answers the smallest of the most frequent values on PostgreSQL, DuckDB, ClickHouse and Databricks, and skips NULL on BigQuery.** Two values as frequent as each other were settled as each engine pleased. DuckDB's `MODE` answered differently from one run to the next: over 200 groups of two tied values, 15 runs gave 15 different answers, 97 groups off the smallest in one. ClickHouse's `topK(1)` is an approximate count whose tie moved between runs too, and it answered 0, not NULL, for a group of NULLs only. DuckDB now reads its values in order (`MODE(x ORDER BY x)`), ClickHouse counts them exactly (`sumMap`, keyed in ascending order, NULL for no values), and Databricks asks for its deterministic `MODE(x, true)`, as PostgreSQL's `MODE() WITHIN GROUP (ORDER BY x)` already answered. BigQuery's `APPROX_TOP_COUNT` counted NULL as a value, so a group of NULL, NULL, NULL, 6 had the mode NULL; it now takes the first of its two most frequent that is not NULL. Snowflake's `MODE` and BigQuery's approximate count still answer one of the most frequent values, which the docs now say. Held across ties in either order, of integers, strings, decimals and dates (`test_mode_exec.py`, six engines).
- **PostgreSQL's covariance, correlation and regression, and MySQL's variance and standard deviation, of integers and decimals are exact past a double's 53 bits.** Both read their values as doubles, so a value past 2^53, or a decimal of more than about sixteen digits, lost its last digits before anything was subtracted: over 10^17 + 0..5 against a second column, PostgreSQL's covariances came back 0, its correlation NULL and its slope 0, and MySQL's variance was 0, as it was for the `DECIMAL(18, 2)` values 9999999999999999.99 less 0..5 hundredths. Over integers and declared decimals they are now computed from the exact moments Dremio's and Snowflake's statistics already use, summed in `NUMERIC` on PostgreSQL and in `DECIMAL(65, 0)` on MySQL. A group whose sum of squares reaches 10^300 units on PostgreSQL, what the double the result is rounded to holds, or 10^63 on MySQL, keeps the engine's own, as does a decimal of more than 150 places, whose powers of ten no double holds. PostgreSQL's own variance of an integer or a decimal is `NUMERIC`, exact, and is kept. Held to the exact statistic of seeded groups out to `BIGINT`'s and each decimal's width (`test_exact_statistics_exec.py`). A probe of all eight engines found the others wrong past 2^53 too; the 128-bit ones (DuckDB, Snowflake, Dremio, Databricks) can be exact only while a group's sum of squares fits 128 bits.
- **A derived metric across data sources takes the model's `defaultNumericDataType`.** The combine step's model carried only `weekStart` from the model's settings, so a metric over the legs' partial results was typed with the built-in default: with `decimal(18, 4)`, a metric of 0.2478 came back 0.25. The combine model now carries the numeric type too, and not the query's time zone, which the legs read their timestamps in already.
- **Snowflake's covariance, correlation and regression, and Dremio's covariance, of integers and decimals are exact far from zero.** Both subtract sums of products as doubles, over integers and decimals alike: against a second column over 10^9 + 0..9, a covariance of 18.5 came back 0 on Snowflake, with `corr` and the regressions NULL, and 142.2 on Dremio; over 10^15 + 0..9, -1.25e14 and 1.56e14. Over integers, and over decimal columns declared with `sqlPrecision` and `sqlScale`, `covar_samp`, `covar_pop`, `corr`, `regr_slope` and `regr_intercept` are now computed there from exact moments, as Dremio's variance is (#690), which they now share in the base dialect (`Dialect.exact_statistic`, replacing `exact_variance`): a pair counts where both of its values are, the co-moment `Sab - Sa * Sb / N` is shifted by both integer means, and the correlation and slope are its ratios, the intercept the first mean less the slope times the second. Snowflake raises past 128 bits in any `SUM` a query computes, in a `CASE` branch not taken too (measured: "Value overflow in a SUM aggregate"), so there a value of 10^13 units or more is left out of the exact sums and its group keeps Snowflake's own statistic, and so does a decimal of more than 25 places, whose unscaled product with 10^scale can pass 128 bits too (a `DECIMAL(38, 37)` of 10^-33 raised "Number out of representable range"). The limits read the values the sums read: a value without its pair is in neither, where (9e18, NULL) beside a covariance of 18.5 had sent the group to the engine's own, 142.2 on Dremio. Dremio's own `covar_pop` over no pair answered 0 and is now NULL, as its `covar_samp` over one pair already was. Snowflake's own variance of a `NUMBER` is exact and kept. Seeded vendor tests hold 30 random groups to the exact statistic within 10^-12 on both engines (the intercept within 10^-12 of its two terms); main answered 41 of Dremio's covariances and 94 of Snowflake's values wrong.
- **A derived metric reads a measure's variance, and a float measure's sum, as the measure's own column does.** A metric's formula inlines its components' aggregates without their casts, which would round them first, and skipped two rewrites a measure's own column gets with them: Dremio's exact `variance` and `stddev`, and a `float` measure's sum or average taken over doubles. Measured with a metric over each: Dremio's standard deviation of 10^9 + 0..9 came back 0, and a `float` measure summing two integer rows of 9e18 came back -4.47e17 on ClickHouse and Dremio, whose integer accumulator wraps. The star planner and the CFL outer query now apply both (`metric_expansion.exact_components`), which keep every digit a double has. A `float` measure's DISTINCT sum of integers, summed exactly as a 38-digit decimal where the accumulator wraps, is now read as a double before anything reads it, as the measure's own column was: in a metric Dremio divided it at 6 places, 2 / 600,000 as 0.0000030000. The exact `AVG` and the widened integer `SUM` are left out, since a formula computes on with what they keep: the exact `AVG` stops at the measure's own places, so the average of 1, 1 and 2 times 3 came back 3.99 on DuckDB, and Dremio divides the `DECIMAL(38, 0)` a widened sum is, at 6 places, so 2 / 600,000 came back 0.0000030000. A metric therefore reads the engine's own average, which drifts past 2^53 on BigQuery, ClickHouse, Databricks, Dremio and DuckDB. A new vendor test runs those metrics, the average times 3, an average in a small quotient, and a formula mixing an average, a deviation and a double sum, on all eight engines.
- **Dremio's variance and standard deviation of integers and decimals are exact far from zero.** Dremio subtracts sums of squares as doubles, so its `STDDEV` and `VARIANCE` cancelled on values far from zero, relative to their spread: the variance of 10^9 + 0..9 (9.1666...) came back 0, of 10^15 + 0..9 2.5e14, of 10^17 + 0..9 negative, with a NaN deviation, and the same for decimals. Over integers, and over a decimal column declared with `sqlPrecision` and `sqlScale`, `stddev`, `stddev_pop`, `variance` and `var_pop` are now computed on Dremio from exact moments (`Dialect.exact_variance`): each value as a whole number of its last place, the group's count, sum and sum of squares in `DECIMAL(38, 0)`, shifted by the integer mean as the federated combine step does, rounded once to a double. A group whose sum of squares reaches 10^37 of those units keeps Dremio's own statistic: past 128 bits Dremio's `SUM` wraps silently (three squares of 9e18 summed to -9.7e37). Doubles and a decimal column without its declared places or of 38 places (whose multiplier, 10^38, Dremio cannot hold) keep Dremio's own. The other seven engines' statistics of integers and decimals were already right far from zero and are unchanged. A new seeded vendor test holds 42 groups (far from zero, negative, of one value, constant, with NULLs, at the limit and past it) to the exact statistic within 10^-12 on Dremio; Dremio's own answered 196 of its 504 values wrong.
- **The OBML schema says which aggregations MySQL and Dremio lack.** The `aggregation` description listed MySQL's missing correlation, covariance and regression but not its missing `mode`, and nothing for Dremio, which has no `mode`, `corr`, `regr_slope` or `regr_intercept` and refuses them at compile time. In the vendored copy too (osi-orionbelt 0.6.1, unreleased).
- **Dremio reads text outside Latin-1.** Dremio types a plain string literal as ISO-8859-1, so a model holding text outside it, such as `'İstanbul'`, `'€'` or `'東京'`, failed on Dremio wherever the text was a value of its own: a CASE branch of a computed column, a `coalesce` fallback, a SELECT item. Compared with a column it ran, but the column was cast for it, so the filter was not pushed down to the scan. Its `_UTF8'...'` form is the reverse: a value runs, a comparison with a column fails ("Cannot apply = to the two different charsets"). Such text is now written `SUBSTR(_UTF8'...', 1)`, which measured right in all thirteen places tried, filters, `IN`, `LIKE`, `ilike`, CASE, `coalesce`, `concat`, UNION and GROUP BY among them, and is pushed down like any filter value; Latin-1 text keeps the plain literal. The SQL validator reads the `_UTF8` prefix too (a Trino-based sqlglot dialect that knows it), so such a query is no longer reported invalid, and the formatted SQL keeps `_UTF8'...'` joined, as Dremio requires. A `listagg` `delimiter` that is not ASCII is refused at compile time: Dremio writes as many UTF-8 bytes of a separator as it has characters, so `' · '` joined `a`, `b`, `c` as `a ·b ·c`, and `'é'` left bytes that are not UTF-8. A vendor test now round-trips such text on all eight engines and filters and aggregates a computed column holding it; on main it fails on Dremio.
- **A total or grain override is the aggregate of its rows, for every aggregation.** `total: true` and a `grain` override were a window over the query's groups, which re-aggregates their values: right for a sum, a count, a minimum, a maximum and an average, and wrong without an error for anything else. A standard deviation's total was the sum of the groups' standard deviations (47.0 for 20.2), a distinct count counted a value once per group it appeared in, and a `distinct: true` average totalled every row (3.5 for 4). Under `rollup` or `cube` the window also added the subtotal rows, so even a sum's total came out three times too large. Such a measure is now computed again in a CTE of its own, over the query's rows, grouped by its grain and joined back, a NULL member to its own group; `median`, the percentiles, `mode`, `first` / `last`, `listagg` and `any_value`, refused with `total: true` before, are computed the same way. A `grain` override under `rollup` or `cube`, which double counted as well (180 for 90), and a total computed apart beside a `filterContext` or a deduplicated measure are refused by name (`INCOMPATIBLE_COMBINATION`). A windowed total is now cast once, after the window: the planner's cast stayed on each group's value, so a sum declared `dataType: integer` over three groups of 0.40 totalled 0 for 1, and a derived metric over a total read the cast value only when the measure was selected beside it (200 for 233.3), and always in a multi-fact query, whose planner records its aggregates cast. A metric now reads each component bare, total or not, selected or not, with the component's own default, as the planner inlines it into a metric without a total (a filtered component with `defaultValue: 0` read NULL beside a total). On ClickHouse a metric over a windowed total selected beside it failed with a window nested in a window, its bare column name resolving to the outer alias; the window now reads the base column qualified. Verified on all eight engines.
- **A federated query no longer counts a row of a repeated object once per join key.** One database sums, counts or averages a measure of an object its joins repeat (customers' ages over their sales) over that object's distinct rows. Across data sources the fact leg deduplicated them within each federation key, so a customer whose sales reached two products of one category was counted twice: the sum of ages 10 and 20 came out 40 for 30, their average 13.33 for 15. Such a query is now refused (`FEDERATION_UNSUPPORTED_AGGREGATION`) unless everything the fact leg groups by beyond the query's dimensions is read from that object or one it joins many-to-one, where each of its rows has one value: the federation keys, and the dimensions a filter after the join reads (an OR across sources); for a `rollup` or `cube` subtotal and a measure's `total: true`, which add groups together, the selected dimensions as well. `min`, `max` and `count_distinct` combine either way.
- **A federated query computes a measure written as an expression.** The planner took a measure with an `expression` for a metric and left it out of the legs, so a query across data sources selecting, say, a `sum` of `{[Orders].[Amount]} * 2` failed with `Unknown measure`. It is computed in the fact leg like any other measure.
- **The statistical aggregates answer the SQL standard's statistic on every engine.** On MySQL, `stddev` and `variance` rendered as its `STDDEV` and `VARIANCE`, which are MySQL's population statistics: measured over 1, 2, 2, 3, 7, 4 they answered 1.95 and 3.81 where the sample statistics are 2.14 and 4.57, and 0 over a single value instead of NULL; they now render `STDDEV_SAMP` and `VAR_SAMP`. ClickHouse's `varSamp` family subtracts sums of squares, which cancel far from zero: the variance of 10^9 + 0..9 came back 0, as integers, decimals or doubles, the covariance 0 and the correlation `nan`; every statistic now renders the numerically stable function (`stddevSampStable`, `varPopStable`, `covarSampStable`, `corrStable` and so on). Where the standard leaves a statistic undefined, the answer is now NULL everywhere: ClickHouse answered `inf` or `nan` for a sample statistic of one value and a correlation of a constant column, DuckDB `NaN` for `corr` and `regr_slope` over one pair or a constant column, BigQuery `NaN` for `corr` of a constant column, Dremio `NaN` for `covar_samp` of one pair; and Databricks failed the whole query with `DIVIDE_BY_ZERO` when a `corr` of a constant column sat beside a covariance or regression of the same query, so its `corr` is now the covariance over the standard deviations through `try_divide`. Dremio cannot parse `CORR`, `REGR_SLOPE` or `REGR_INTERCEPT`, so those are refused at compile time (`UNSUPPORTED_AGGREGATION_FOR_DIALECT`) rather than failing at the database. A new vendor execution test asserts all nine statistics against their exact values on all eight engines, over integers, decimals and doubles, one value, a constant, a NULL and values far from zero; on main it fails on six of them. Still open (strict expected failures in that test, documented): Snowflake over doubles, and its covariance, correlation and regression over integers, and Dremio over every type, also subtract sums of squares and have no stable function, so far from zero they answer 0, NULL or a negative variance.
- **A federated query groups and counts distinct values as MySQL and ClickHouse do.** The combine step compares values in DuckDB, bytewise for a string and with `0.0` equal to `-0.0`, across rows a leg returned from different groups. Measured, a `count_distinct` over a MySQL column counted `'a'` and `'A'`, `'e'` and `'é'`, `'ss'` and `'ß'` as two values each where MySQL counts one, and a group by such a column split the same way; ClickHouse counted `0.0` and `-0.0` as one value where it counts two. A MySQL leg now returns each selected string dimension, and each string a `count_distinct` counts, as one member of its collation's class of equal values, the same member for all of them (`FIRST_VALUE(x) OVER (PARTITION BY x ORDER BY CAST(x AS BINARY))`, which partitions exactly as MySQL's `GROUP BY` does, padding included, under every collation probed); a ClickHouse leg returns a counted float as its text. A filter the combine step runs still reads the value the leg had. A new vendor execution test compares a federated query with each engine's own answer on all eight engines; on main it fails on MySQL and ClickHouse alone. A ClickHouse float dimension, cross-source join keys and string `MIN`/`MAX` still compare as DuckDB does (documented).

- **An average of a decimal column is exact on DuckDB, ClickHouse and Dremio, and an integer average rounds on ClickHouse.** Their `AVG` of a decimal is a double, so an average past fifteen digits drifted and one at its type's width broke: measured, 12345678901234.565 came back .56 on DuckDB and ClickHouse (.57 is right), and 9999999999999999.99 came back 1E+16, which DuckDB's own cast refused, ClickHouse returned as 1E+16 and Dremio turned into 0. Each now sums the decimal exactly and divides it exactly, each value summed at its own scale and the total narrowed only by truncating: DuckDB in integer arithmetic (the routine federated averages use), ClickHouse with `divideDecimal` over a `Decimal256` sum, Dremio by long division in `DECIMAL(38, 0)` integers. ClickHouse's integer average divided with `divideDecimal` at the result's own scale, which truncates, so 1, 2 and 2 averaged to 1.66; it now divides two places further and the cast rounds it to 1.67 (two, because `divideDecimal` returns 0 for a dividend under ten units of its result scale, and a single 0.005 averaged to 0.00 one place further). An average rounded at a few places and then by the measure's cast can round twice: 100 ones among 20001 rows average 0.0049997, which is 0.00, but came back 0.01 from Dremio's and Databricks' integer averages (each decimal quotient is rounded at `max(6, scale)` places), Snowflake's integer `AVG` (6 places) and Databricks' decimal `AVG` (four places more than the column), Snowflake's decimal `AVG` (8 places) did the same over 2000001 rows, and BigQuery's (`NUMERIC`, 9 places) for integers and decimals over 20000001. Dremio, Databricks and Snowflake now divide in integers, each division of an exact multiple, to 18 places, truncated, and BigQuery averages in `BIGNUMERIC` (38 places) and truncates that, so the measure's cast rounds once and a period-over-period or window wrapper reads the unrounded average; Dremio and Databricks keep their single division from 6 to 14 places, where it rounds once already. Where a route has no exact room (the integer long division past 17 places, or a result or declared column with more integer digits than it holds, ClickHouse past a result precision of 74 or a declared column of 58 digits, DuckDB past 18 places) the engine's own `AVG` is kept. Only columns declared `decimal` are rewritten; a `float` column is averaged as a double, as on every engine. PostgreSQL and MySQL are left as they were. The vendor execution test now covers decimal averages on all eight engines, Dremio included, and DuckDB, which it had skipped since before its exact integer route.
